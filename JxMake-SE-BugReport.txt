[BUG-1] Last render silently dropped when rate-limiter fires
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : _renderBuffer()

Description:
  When _renderBuffer() is called and the 50 ms cooldown has NOT yet elapsed,
  the method clears _rbPending and returns immediately without scheduling any
  future render. If no further write arrives after the cooldown expires, the
  last dirty data is never rendered — the screen appears frozen until the next
  unrelated update.

Why it matters:
  Any burst of output (e.g. a fast-finishing build) whose last chunk arrives
  within the 50 ms window is silently lost on screen.

Fix:
  When the cooldown prevents immediate rendering, post a delayed invocation
  instead of simply returning, so the render is guaranteed to run once the
  cooldown expires. The _update_scheduler (already available in JxMakeRootPane)
  can be used for this, or a separate single-thread scheduler owned by
  JxMakeConsole:

    if (now - _rbLastRun.get() < 50) {
        // reschedule instead of dropping
        _update_scheduler.schedule(
            () -> SwingUtilities.invokeLater(this::_renderBuffer),
            50 - (now - _rbLastRun.get()), TimeUnit.MILLISECONDS);
        _rbPending.set(false);
        return;
    }

  Note: the rescheduled call will itself check the cooldown flag and proceed
  normally. Care must be taken to avoid scheduling multiple pending timers if
  writes continue to arrive during the delay; keeping _rbPending set until
  the scheduled call fires is sufficient.
[DONE]


[BUG-2] _blinkMap holds stale document offsets after scroll
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : _scrollBufferOneUp(), handleUpdate()

Description:
  _scrollBufferOneUp() removes the first line from the StyledDocument but does
  NOT prune or adjust the character offsets stored in _blinkMap. On the next
  blink cycle, handleUpdate() applies those now-stale offsets via
  _textSDoc.setCharacterAttributes(), which either silently corrupts the wrong
  text range or throws a BadLocationException.

Why it matters:
  Blink rendering can corrupt visible text or produce spurious exceptions
  whenever the buffer scrolls.

Fix:
  In _scrollBufferOneUp() (and _scrollBufferOneDown_ifCurRowIsZero()), rebuild
  or adjust _blinkMap: remove entries whose row was scrolled away and shift
  the document offsets of surviving entries by the number of characters
  removed/added. The simplest safe approach is to call _blinkMap.clear() after
  every scroll and let _renderRow() repopulate it for the now-dirty rows. The
  added re-render cost is acceptable because scrolls already mark rows dirty.
[DONE]


[BUG-3] ED 'J' type-1 (clear to beginning of screen) uses exclusive loop bound,
        leaving the cursor row only partially marked dirty
--------------------------------------------------------------------------------
File   : ANSIScreenBuffer.java
Where  : _processCSI(), case 'J', shared case 0/1 block

Description:
  For ESC[1J the VT standard says "clear from the beginning of the screen to
  the cursor position, inclusive of the cursor cell". The implementation uses
  a shared case 0/1 block:
      begC = 0;          endC = _curCol + 1;      // cursor-row column range
      begR = 0;          endR = _curRow;           // multi-row range (exclusive)
  The cursor row is cleared via:
      for (i = begC; i < endC; ...)  // clears columns 0.._curCol on _curRow
  The rows above the cursor are cleared via:
      for (i = begR; i < endR; ...)  // clears rows 0.._curRow-1 (exclusive)
  Both loops are correct in terms of which cells are erased.

  The issue is the dirty-marking that follows:
      _screenBuffer.dirty[_curRow] = true;          // marks cursor row
      for (i = begR; i < endR; ...) dirty[i] = true; // marks rows 0.._curRow-1

  For the type==1 case, endR = _curRow, so dirty is marked for _curRow (via
  the first line) and for rows 0.._curRow-1 (via the loop). This is correct
  when _curRow > 0. However, when _curRow == 0, endR == begR == 0, the loop
  does not execute, and only dirty[0] is set — which is also correct.

  The real concern is structural: the type==1 clear is composed of two
  independent loops operating on different row ranges (_curRow alone vs.
  0.._curRow-1), making the logic harder to audit and easy to break in a
  future refactor. Unlike type==0 (cursor-to-end), where rows above the
  cursor are a separate range, type==1 should conceptually clear a contiguous
  block from row 0 to _curRow inclusive.

Why it matters:
  The current behavior is functionally correct for well-formed cursor positions.
  The risk is maintenance: the asymmetric structure (cursor row handled
  separately from the range loop) is easy to mis-edit into an off-by-one.

Fix:
  Unify into a single pass for type==1: iterate from row 0 to _curRow
  inclusive, clearing columns 0..(numCols-1) for rows < _curRow and 0.._curCol
  for row == _curRow. Mark all touched rows dirty in one place:

    // type == 1: clear from beginning of screen to cursor (inclusive)
    for (int r = 0; r <= _curRow; ++r) {
        int c0 = 0;
        int c1 = (r < _curRow) ? _screenBuffer.numCols : (_curCol + 1);
        for (int c = c0; c < c1; ++c)
            _screenBuffer.rows[r].cols[c].setSpace(bgc, fgc);
        _screenBuffer.dirty[r] = true;
    }
    _screenBuffer.anyDirty = true;
[DONE]


[BUG-4] Integer.valueOf() used where parseInt() is appropriate
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : SavedEnvVarState.load() (inner class deserialization)

Description:
  Integer.valueOf(strChk) and Integer.valueOf(strEffCount) are used to parse
  line-read strings into ints. Integer.valueOf() returns a boxed Integer which
  is immediately auto-unboxed, and raises NumberFormatException (not caught)
  on malformed input. Using Integer.parseInt() is the conventional idiom,
  avoids unnecessary boxing, and more clearly signals the intent.

Why it matters:
  Minor style/efficiency issue. NumberFormatException on a corrupt file will
  bubble uncaught and silently truncate the state load (due to the early-return
  error handling pattern), which is acceptable behavior but the root cause
  would be unclear in a stack trace.

Fix:
  Replace Integer.valueOf(str) with Integer.parseInt(str) at both call sites.
[DONE]


[BUG-5] JxMakeShell file I/O uses platform-default charset
--------------------------------------------------------------------------------
File   : JxMakeShell.java
Where  : _saveAllAliases(), _loadAllAliases()

Description:
  new FileWriter(...) and new FileReader(...) use the JVM's default charset,
  which varies by OS and locale. On Windows with a non-UTF-8 locale (e.g.
  a CJK system locale), alias names containing non-ASCII characters will be
  corrupted when saved and then loaded.

Why it matters:
  Alias names with non-ASCII characters will be silently corrupted on systems
  where the JVM default charset is not UTF-8.

Fix:
  Use the explicit charset variant:
    new OutputStreamWriter(new FileOutputStream(path), StandardCharsets.UTF_8)
    new InputStreamReader(new FileInputStream(path),  StandardCharsets.UTF_8)

  The same issue exists in JxMakeRootPane.Config.save() (FileWriter) and
  in _saveTextFile_impl() / _loadTextFile_impl() (FileWriter/FileReader),
  although for JxMake script files the user's intent may be to use the system
  encoding. The alias and command-history files should definitely be UTF-8.
[DONE]


[CLEANUP-1] JxMakeRootPane._instance is a non-volatile mutable static
--------------------------------------------------------------------------------
File   : JxMakeRootPane.java
Where  : static field _instance, constructor, static helper methods

Description:
  _instance is assigned in the constructor and read from static methods called
  from background threads (e.g. from JxMakeShell). The field is not volatile
  and there is no synchronization around its write. In practice a single
  instance is used, but the Java Memory Model does not guarantee visibility
  of the assignment to other threads without a memory barrier.

Why it matters:
  Theoretical but real: a background thread could see _instance == null or a
  partially constructed object.

Fix:
  Declare _instance as volatile, or better, use a proper singleton
  initialization pattern (e.g. initialize-on-demand holder or pass the
  instance explicitly to JxMakeShell instead of relying on the global).
[DONE]


[CLEANUP-2] _renderUpTo() re-renders all rows 0..rowNum unconditionally
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : _renderUpTo(int rowNum)

Description:
  _renderUpTo iterates every row from 0 to rowNum and calls _renderRow(r) for
  each. _renderRow() does check the dirty flag and skips clean rows, but the
  loop overhead (and document-offset computation inside _renderRow) is still
  paid for every row on every render pass. For a 64-screen buffer (up to
  3072 rows) this is O(N) work per render cycle.

Why it matters:
  Performance: on large scroll buffers the render path is slower than needed.

Fix:
  Either iterate only dirty rows (maintain a set or scan the dirty[] array
  for set flags), or only render rows >= _lastRenderedRow when no scroll has
  occurred.
[NOT A FIX - IT IS A REGRESSION]

[CLEANUP-4] _menuItems HashMap in JxMakeRootPane_Menu is module-level static
             state
--------------------------------------------------------------------------------
File   : JxMakeRootPane_Menu.java
Where  : static field _menuItems

Description:
  _menuItems is a static HashMap shared across all instances. Because only one
  JxMakeRootPane ever exists this is fine in practice, but it prevents clean
  re-initialization if the editor is ever embedded multiple times. Additionally,
  _usedMnemonic is a static String that accumulates state across calls to
  _createMenu(), and is not reset between instances.

Fix:
  Either accept the single-instance assumption and document it clearly, or
  convert these to instance fields (passed into the static helpers), or reset
  them at the start of createMenuBar().

[CLEANUP-5] APP_DATA_DIRECTORY and related path strings are non-final statics

[CLEANUP-6] _update_scheduler uses newScheduledThreadPool(1) with no shutdown
--------------------------------------------------------------------------------
File   : JxMakeRootPane.java
Where  : field _update_scheduler, constructor / doLayout

Description:
  The ScheduledExecutorService created with newScheduledThreadPool(1) is never
  explicitly shut down. The thread pool holds a non-daemon thread that will keep
  the JVM alive after the window is closed if the JVM shutdown hook is not
  triggered promptly.

Fix:
  Override a dispose/cleanup method (or hook into the window-closing event) to
  call _update_scheduler.shutdown() (and similarly _updateInclude_scheduler if
  it exists).
[DONE]

[TM-BUG-1] _inEvalStatment not restored when startTokenType is not Null or
            Comment
--------------------------------------------------------------------------------
File   : JxMakeTokenMaker.java
Where  : getTokenList(), field _inEvalStatment

Description:
  getTokenList() resets _inStringML and _inEvalStatment only when
  startTokenType == TType.Null. For continuation lines (startTokenType ==
  some multi-line token type), _inEvalStatment retains its value from the
  previous call. This is correct for _inStringML-style multi-line contexts.
  However, _inEvalStatment is a per-line piece of state that tracks whether
  the current line is inside an eval statement (0 = before ':=', 1 = after
  ':='). An eval statement does NOT naturally span multiple RSyntaxTextArea
  lines the way a multiline string does (eval ends at ';' or logical line
  end). If a line continuation (\) is used inside an eval statement,
  _inEvalStatment is carried forward and the trailing addEmptyTokenEP() causes
  RSyntaxTextArea to pass a non-Null startTokenType to the next line, but the
  actual token type encoding for "eval continuation" is overloaded with the
  _inStringML token type, making the two indistinguishable at the getTokenList
  entry point.

Fix:
  Introduce a dedicated token type (or a reserved bit in the startTokenType
  integer) to distinguish "inside eval continuation" from "inside multiline
  string". At the getTokenList entry point, check for the eval-continuation
  marker and restore _inEvalStatment accordingly, independent of the
  _inStringML restoration path.
[DONE]


[TM-BUG-2] Keyword-at-start-of-line check scans within the token instead of
            before it
--------------------------------------------------------------------------------
File   : JxMakeTokenMaker.java
Where  : _ctxTask_Keyword(), the loop that checks for preceding non-whitespace

Description:
  The guard that enforces "keyword must be the first token on the logical line"
  iterates backwards to check whether any non-whitespace character precedes the
  keyword on the current line. However, the loop starts at _gtl_detPos - 1
  (one before the detected token's end) rather than _gtl_curPos - 1 (one
  before the token's start), so it scans within the token itself instead of
  before it.

  In practice _gtl_curPos == segment.offset at the very start of processing,
  so for the first token on a line the scan is a no-op (the loop may not
  execute at all). This appears to work by coincidence for the common case but
  the intent and the implementation differ.

Fix:
  Change the scan start to _gtl_curPos - 1 so it actually scans characters
  before the current token:
      for (int i = _gtl_curPos - 1; i >= _gtl_segment.offset; --i) { ... }
[DONE]

[TM-WORKAROUND-1] Multi-line comments (*...*) fold incorrectly when nested
--------------------------------------------------------------------------------
File   : JxMakeFoldParser.java
Where  : getFolds(), case TType.Comment, opening marker check

Description:
  The grammar supports nested block comments: (* outer (* inner *) still
  outer *). JxMakeFoldParser only recognises a single level: it pushes a fold
  on "(*" and pops on the first "*)". With nested comments the inner "*)"
  prematurely closes the outer fold.

  This is a known RSyntaxTextArea limitation (the token stream sees a single
  TType.Comment span for the entire nested comment), so a perfect fix is not
  possible. However, the fold parser can work around it:

Workaround (light):
  Maintain a nesting counter in the fold parser (mirroring
  _gtl_nestedMLComment in the tokenizer). Only actually pop the fold when the
  counter reaches zero. Track the counter in the getFolds() loop by scanning
  the token text for occurrences of "(*" and "*)" within each TType.Comment
  token.

  Note: this won't produce nested fold markers (nested comment folds will look
  flat) but it prevents premature fold closure.
[DONE]


[TM-WORKAROUND-2] One-liner 'if' with ':' is folded identically to block 'if'
--------------------------------------------------------------------------------
File   : JxMakeFoldParser.java
Where  : getFolds(), case TType.SOperator, ':' check

Description:
  Grammar: "if <cond> : <stmt>" is a single-line if (no endif).
           "if <cond>\n  <body>\nendif" is a block if (requires endif).

  The fold parser opens a fold on every 'if' keyword token and expects either
  ':' (one-liner) or 'endif' (block) to close it. The ':' close path correctly
  collapses the fold. However, ':' is also a valid operator in other contexts
  (e.g., eval expressions, ternary operators). The current guard checks
  _expectedStack.peek().equals("endif"), which is correct — it only triggers
  when a fold is open AND the top of the expected stack is "endif". If the ':'
  appears in an eval context on the same line as an 'if', the fold will be
  incorrectly closed.

  RSyntaxTextArea cannot fully distinguish these cases without a complete
  context-aware parser, so a perfect fix is not possible.

Workaround (light):
  In the TType.SOperator ':' handler, additionally verify that no other
  non-whitespace token appeared between the 'if' and the ':' on the current
  line (i.e. the ':' is the immediate token after the condition expression).
  This requires tracking a "last keyword was 'if'" flag per line in getFolds().
[NOT WORTH DOING]


[TM-NOTE-1] Context stack is not preserved across lines (by design, documented)
--------------------------------------------------------------------------------
File   : JxMakeTokenMaker.java

Description:
  RSyntaxTextArea's contract requires that per-line state be encoded entirely
  in the integer startTokenType passed to getTokenList(). The JxMakeTokenMaker
  persists _contextStack, _inStringML, and _inEvalStatment as instance fields
  across calls, which works for strictly sequential top-to-bottom parsing but
  can produce incorrect results when RSyntaxTextArea re-parses a single line
  in isolation (e.g. after a single-line edit). The file's header comment
  documents this limitation.

  This is an inherent tokenizer limitation and is not directly fixable without
  a complete rewrite using RSyntaxTextArea's multi-state token type system
  (encoding full context in the token type integer). It is recorded here for
  completeness.

Workaround potential:
  Encode the top-of-stack context as part of the returned token type for the
  most common multi-line contexts (StringML, eval continuation). This is
  already partially done for _inStringML. Extending it to the full context
  stack would require reserving token type ranges per context — feasible for
  the 2-3 most important contexts but not for the full stack depth.
[NOT APPLICABLE - ALREADY DONE IN PREVIOUS _inEvalStatment FIXES]
