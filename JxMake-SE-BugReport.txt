PART 1 – SCRIPT EDITOR AND CONSOLE
================================================================================


[BUG-1] Last render silently dropped when rate-limiter fires
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : _renderBuffer()

Description:
  When _renderBuffer() is called and the 50 ms cooldown has NOT yet elapsed,
  the method clears _rbPending and returns immediately without scheduling any
  future render. If no further write arrives after the cooldown expires the
  last dirty data is never rendered — the screen appears frozen until the next
  unrelated update.

Why it matters:
  Any burst of output (e.g. a fast-finishing build) whose last chunk arrives
  within the 50 ms window is silently lost on screen.

Fix:
  When the cooldown prevents immediate scheduling, post a delayed invocation
  (e.g. via ScheduledExecutorService or SwingUtilities with a slight delay) so
  the render is guaranteed to run once the cooldown expires. Alternatively,
  use a "pending reschedule" flag rather than simply dropping the request.

  Sketch:
    if (now - _rbLastRun.get() < 50) {
        // reschedule instead of dropping
        _update_scheduler.schedule(() -> SwingUtilities.invokeLater(this::_renderBuffer_impl),
            50 - (now - _rbLastRun.get()), TimeUnit.MILLISECONDS);
        _rbPending.set(false);
        return;
    }


[BUG-2] _blinkMap holds stale document offsets after scroll
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : _scrollBufferOneUp(), handleUpdate()

Description:
  _scrollBufferOneUp() removes the first line from the StyledDocument but does
  NOT prune or adjust the character offsets stored in _blinkMap. On the next
  blink cycle, handleUpdate() applies those now-stale offsets via
  _textSDoc.setCharacterAttributes(), which either silently corrupts the
  wrong text range or throws a BadLocationException.

Why it matters:
  Blink rendering can corrupt visible text or produce spurious exceptions
  whenever the buffer scrolls.

Fix:
  In _scrollBufferOneUp() (and _scrollBufferOneDown_ifCurRowIsZero()), rebuild
  or adjust _blinkMap: remove entries whose row was scrolled away and shift
  offsets of surviving entries by the number of characters removed/added.
  Simplest safe approach: call _blinkMap.clear() after every scroll, then let
  _renderRow() repopulate it for dirty rows. The added re-render cost is
  acceptable because scrolls already mark rows dirty.


[BUG-3] ED 'J' type-1 (clear to beginning of screen) uses exclusive end row
--------------------------------------------------------------------------------
File   : ANSIScreenBuffer.java
Where  : _processCSI(), case 'J', type==1

Description:
  For ESC[1J the VT standard says "clear from cursor to the BEGINNING of the
  screen, inclusive of the cursor row". The implementation computes:
      begR = 0;
      endR = _curRow;          // loop: for (i = begR; i < endR; ...)
  The cursor row itself is cleared via the column loop, but rows 0.._curRow-1
  are iterated with strict-less-than, so row _curRow-1 IS cleared – however
  the issue is the column range for the current row. begC=0, endC=_curCol+1
  is correct, but then the multi-row loop (begR=0, endR=_curRow exclusive)
  does NOT include _curRow. That row is cleared separately via the column loop,
  which is correct for EL. However, the dirty marking only marks _curRow and
  the range [begR, endR), so if begR == endR (cursor at row 0) no multi-row
  dirty flags are set and nothing above is marked. This is fine for row 0, but
  the overall asymmetry means any programmatic audit is confusing, and an
  off-by-one is easy to introduce on future edits.

  Separately: the EL 'K' type-1 case uses endC = _curCol+1 with i < endC
  which correctly includes the cursor cell. The ED type-1 uses begR=0 /
  endR=_curRow with i < endR, which intentionally excludes _curRow (handled
  separately). This is technically correct but the two separate clear operations
  are not atomic in the dirty-flag sense.

Why it matters:
  Borderline correctness issue; behavior diverges from VT spec when dirty flag
  updates are considered. Low immediate risk but a latent source of off-by-one
  if the clearing logic is ever refactored.

Fix:
  Unify into a single pass: iterate from row 0 to _curRow (inclusive), clearing
  columns 0..(numCols-1) for rows < _curRow and 0.._curCol for row == _curRow.
  Mark all touched rows dirty in one place.


[BUG-4] Integer.valueOf() used where parseInt() is appropriate
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : SavedEnvVarState.load() (inner class deserialization)

Description:
  Integer.valueOf(strChk) and Integer.valueOf(strEffCount) are used to parse
  line-read strings into ints. Integer.valueOf() returns a boxed Integer which
  is immediately auto-unboxed, and raises NumberFormatException (not caught)
  on malformed input. Using Integer.parseInt() is the conventional idiom,
  avoids unnecessary boxing, and more clearly signals the intent.

Why it matters:
  Minor style/efficiency issue. NumberFormatException on corrupt file will
  bubble uncaught and silently truncate the state load (due to early-return
  error handling pattern), which is acceptable behavior but the root cause
  would be unclear in a stack trace.

Fix:
  Replace Integer.valueOf(str) with Integer.parseInt(str) at both call sites.


[BUG-5] JxMakeShell file I/O uses platform-default charset
--------------------------------------------------------------------------------
File   : JxMakeShell.java
Where  : _saveAllAliases(), _loadAllAliases()

Description:
  new FileWriter(...) and new FileReader(...) use the JVM's default charset,
  which varies by OS and locale. On Windows with a CJK locale the default may
  not be UTF-8, corrupting alias names containing non-ASCII characters.

Why it matters:
  Alias names with non-ASCII characters will be corrupted when saved/loaded
  on systems where the default charset is not UTF-8.

Fix:
  Use the explicit charset variant:
    new OutputStreamWriter(new FileOutputStream(path), StandardCharsets.UTF_8)
    new InputStreamReader(new FileInputStream(path),  StandardCharsets.UTF_8)
  The same issue exists in JxMakeRootPane.Config.save() (FileWriter) and
  _saveTextFile_impl() / _loadTextFile_impl() (FileWriter/FileReader), although
  for script files the user's intent might be to use the system encoding.
  The alias/history files should definitely be UTF-8.


[CLEANUP-1] JxMakeRootPane._instance is a non-volatile mutable static
--------------------------------------------------------------------------------
File   : JxMakeRootPane.java
Where  : static field _instance, constructor, static helper methods

Description:
  _instance is assigned in the constructor and read from static methods called
  from background threads (e.g. JxMakeShell). The field is not volatile and
  there is no synchronization around its write. In practice a single instance
  is used, but the JMM does not guarantee visibility without a memory barrier.

Why it matters:
  Theoretical but real: a background thread could see _instance == null or a
  partially constructed object.

Fix:
  Declare _instance as volatile, or better, use proper singleton initialization
  (e.g. initialize-on-demand or pass the instance explicitly to JxMakeShell
  instead of relying on the global).


[CLEANUP-2] _renderUpTo() re-renders all rows 0..rowNum unconditionally
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : _renderUpTo(int rowNum)

Description:
  _renderUpTo iterates every row from 0 to rowNum and calls _renderRow(r) for
  each. _renderRow() does check the dirty flag and skips clean rows, but the
  loop overhead (and document-offset computation inside _renderRow) is still
  paid for every row on every render pass. For a 64-screen buffer (up to
  3072 rows) this is O(N) work per render cycle.

Why it matters:
  Performance: on large scroll buffers the render path is slower than needed.

Fix:
  Either iterate only dirty rows (maintain a set or scan the dirty[] array),
  or only render rows >= _lastRenderedRow when no scroll has occurred.


[CLEANUP-3] Typo in comment: "Dicard" should be "Discard"
--------------------------------------------------------------------------------
File   : JxMakeConsole.java
Where  : SavedEnvVarState.load() — comments on readLine() calls

Description:
  "Dicard the '\n'" appears twice. Minor typo, no functional impact.

Fix:
  Correct to "Discard".


[CLEANUP-4] _menuItems HashMap in JxMakeRootPane_Menu is module-level static state
--------------------------------------------------------------------------------
File   : JxMakeRootPane_Menu.java
Where  : static field _menuItems

Description:
  _menuItems is a static HashMap shared across all instances. Because only one
  JxMakeRootPane ever exists this is fine in practice, but it prevents clean
  re-initialization if the editor is ever embedded multiple times. Additionally,
  _usedMnemonic is a static String that accumulates state across calls to
  _createMenu(), which is also not reset between instances.

Fix:
  Either accept the single-instance assumption and document it clearly, or
  convert these to instance fields passed into the static helpers, or reset
  them at the start of createMenuBar().


[CLEANUP-5] APP_DATA_DIRECTORY and related path strings are non-final statics
--------------------------------------------------------------------------------
File   : JxMakeRootPane.java
Where  : static fields APP_DATA_DIRECTORY, SCRIPT_EDITOR_STATE, etc.

Description:
  These fields are declared as "private static String" but are never reassigned.
  They should be "private static final String" to express immutability and allow
  JIT optimization.

Fix:
  Add the final modifier to APP_DATA_DIRECTORY, SCRIPT_EDITOR_STATE,
  SCRIPT_FILE_STATE, CONSOLE_CMD_HIST, CONSOLE_CMD_ALIAS, CONSOLE_ENV_PREFIX.


[CLEANUP-6] _update_scheduler uses newScheduledThreadPool(1) with no shutdown
--------------------------------------------------------------------------------
File   : JxMakeRootPane.java
Where  : field _update_scheduler, constructor / doLayout

Description:
  The ScheduledExecutorService created with newScheduledThreadPool(1) is never
  explicitly shut down. The thread pool holds a non-daemon thread and will keep
  the JVM alive even after the window is closed if a JVM shutdown hook is not
  triggered promptly.

Fix:
  Override a dispose/cleanup method (or hook into the window-closing event) to
  call _update_scheduler.shutdown() (and similarly _updateInclude_scheduler).

PART 2 – JXMAKE SYNTAX HIGHLIGHTER (JxMakeTokenMaker)
================================================================================
Grammar reference: docs/txt/JxMake-Grammar.txt and related doc files.


[TM-BUG-1] _inEvalStatment not restored when startTokenType is not Null or Comment
--------------------------------------------------------------------------------
File   : JxMakeTokenMaker.java
Where  : getTokenList(), field _inEvalStatment

Description:
  getTokenList() resets _inStringML and _inEvalStatment only when
  startTokenType == TType.Null. For continuation lines (startTokenType ==
  some multi-line token type), _inEvalStatment retains its value from the
  previous call, which is correct for _inStringML-style multi-line contexts.
  However, _inEvalStatment is a per-line piece of state that tracks whether the
  current line is inside an eval statement (0 = before ':=', 1 = after ':=').
  An eval statement does NOT naturally span multiple RSyntaxTextArea lines the
  way a multiline string does (eval ends at ';' or logical line end). If a line
  continuation (\) is used inside an eval statement, _inEvalStatment is carried
  forward and the trailing addEmptyTokenEP() causes RSyntaxTextArea to pass a
  non-Null startTokenType to the next line, but the actual token type encoding
  for "eval continuation" is overloaded with the _inStringML token type, making
  the two indistinguishable at the getTokenList entry point.

Why it matters:
  On a line following a line-continued eval statement the tokenizer enters
  with a non-Null startTokenType but _inEvalStatment == -1 (reset only for
  Null), so the eval-operator highlighting is lost for continuation lines.

Fix:
  Introduce a dedicated token type (e.g. TType.EvalStatement) to distinguish
  eval-continuation from string-ML-continuation, and restore _inEvalStatment
  appropriately when startTokenType == TType.EvalStatement.


[TM-BUG-2] JxMakeFoldParser._pop() does not guard against empty _expectedStack
--------------------------------------------------------------------------------
File   : JxMakeFoldParser.java
Where  : _pop(Token token)

Description:
  _pop() calls _expectedStack.pop() unconditionally. The call sites check
  _expectedStack.isEmpty() BEFORE calling _pop(), but the check and pop are not
  atomic. If future code paths reach _pop() without the guard, or if the guard
  condition is wrong (e.g. mismatched nesting), EmptyStackException will be
  thrown at runtime. The exception is caught by the outer try/catch but silently
  discards the rest of the fold computation for that parse.

Why it matters:
  Defensive programming: a malformed source file or a tokenizer edge case can
  cause a silent fold failure with no diagnostic.

Fix:
  Add a guard at the top of _pop():
    if (_expectedStack.isEmpty() || _currentFold == null) return;


[TM-BUG-3] Keyword highlighting requires preceding whitespace for line-start keywords
--------------------------------------------------------------------------------
File   : JxMakeTokenMaker.java
Where  : _ctxTask_Keyword()

Description:
  The keyword detection loop:
    for (int i = _gtl_detPos - 1; i > 0; --i) {
        if (isWhitespace(array[i])) continue;
        if (array[i] == '\n') break;
        return false;
    }
  returns false if any non-whitespace character exists before the keyword on
  the same line. This correctly implements "keyword must be the first token on
  the logical line". However, the loop starts at _gtl_detPos - 1 (one before
  the detected token's end) rather than _gtl_curPos - 1 (one before the
  token's start), scanning within the token itself instead of before it.

  In practice _gtl_curPos == segment.offset at the start of processing so for
  the very first token on a line the scan is a no-op (loop doesn't execute
  because i starts at _gtl_detPos-1 which may be >= _gtl_curPos). This appears
  to work by coincidence for common cases but the intent and the implementation
  differ.

Fix:
  Change the scan start to _gtl_curPos - 1 so it actually scans characters
  before the token:
    for (int i = _gtl_curPos - 1; i >= _gtl_segment.offset; --i) { ... }

[TM-WORKAROUND-1] Multi-line comments (*...*) fold incorrectly when nested
--------------------------------------------------------------------------------
File   : JxMakeFoldParser.java
Where  : getFolds(), case TType.Comment, opening marker check

Description:
  The grammar supports nested block comments: (* outer (* inner *) still outer *).
  JxMakeFoldParser only recognises a single level: it pushes a fold on "(*" and
  pops on the first "*)". With nested comments the inner "*)" prematurely closes
  the outer fold.

  This is a known RSyntaxTextArea limitation (the token stream sees a single
  TType.Comment span for the entire nested comment), but the fold parser could
  work around it:

Workaround (light):
  Maintain a nesting counter in the fold parser (mirroring _gtl_nestedMLComment
  in the tokenizer). Only actually pop the fold when the counter reaches zero.
  Track the counter in the getFolds() loop by scanning the token text for
  occurrences of "(*" and "*)" within each TType.Comment token.

  Note: this won't be pixel-perfect (nested comment folds look flat) but it
  prevents premature fold closure.


[TM-WORKAROUND-2] One-liner 'if' with ':' is folded identically to block 'if'
--------------------------------------------------------------------------------
File   : JxMakeFoldParser.java
Where  : getFolds(), case TType.SOperator, ':' check

Description:
  Grammar: "if <cond> : <stmt>" is a single-line if (no endif).
  "if <cond>\n  <body>\nendif" is a block if (requires endif).

  The fold parser opens a fold on every 'if' keyword token and expects either
  ':' (one-liner) or 'endif' (block) to close it. The ':' close path correctly
  collapses the fold. However, ':' is also a valid operator in other contexts
  (e.g., eval expressions, ternary operators). The current guard checks
  _expectedStack.peek().equals("endif"), which is correct, but only triggers
  when a fold is open AND the top of the expected stack is "endif". If the ':'
  appears in an eval context on the same line as an 'if', the fold will be
  incorrectly closed.

  RSyntaxTextArea cannot fully distinguish these without a complete context-
  aware parser, so a perfect fix is not possible.

Workaround (light):
  In the TType.SOperator ':' handler, additionally verify that the ':' token
  is followed immediately (on the same line, no intervening keyword/value tokens
  between the 'if' and ':') by checking that no other non-whitespace token
  appeared between the 'if' and the ':' on the current line. This requires
  tracking a "last keyword was 'if'" flag per line in getFolds().


[TM-NOTE-1] Context stack is not preserved across lines (by design, documented)
--------------------------------------------------------------------------------
File   : JxMakeTokenMaker.java

Description:
  RSyntaxTextArea's contract requires that per-line state be encoded entirely
  in the integer startTokenType passed to getTokenList(). The JxMakeTokenMaker
  persists _contextStack, _inStringML, and _inEvalStatment as instance fields
  across calls, which works for strictly sequential top-to-bottom parsing but
  can produce incorrect results when RSyntaxTextArea re-parses a single line
  in isolation (e.g. after a single-line edit). The file's header comment
  documents this limitation.

  This is an inherent tokenizer limitation and is not directly fixable without
  a complete rewrite using RSyntaxTextArea's multi-state token type system
  (encoding full context in the token type int). It is recorded here for
  completeness.

Workaround potential:
  Encode the top-of-stack context as part of the returned token type for the
  most common multi-line contexts (StringML, eval continuation). This is
  already partially done for _inStringML. Extending it to the context stack
  would require reserving token type ranges per context — feasible for the 2-3
  most important contexts but not for the full stack.
