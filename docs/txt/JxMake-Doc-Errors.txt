FILE     : docs/txt/en_US/04-Defining-Variables.txt
LOCATION : Section "Defining Variables" -- assignment operators description
ISSUE    : The manual lists concatenation assignments as:
               Concatenation assignments (+=) and (:+= or +:=)
           It presents the two direct-concatenation forms as '(:+= or +:=)' but does NOT make
           clear which is the canonical form and which is an alternate spelling.
CORRECT  : Both ':+=' and '+=:' (and '+:=') are accepted.  Scripts exclusively use ':+=' as the
           direct form (e.g. 'CppArchFlags +:= ...' in C++BuildTool_MSVC.jxm and many others).
           The manual's parenthetical '(:+= or +:=)' is internally correct but misleadingly terse.
           The description should explicitly state: ':+=' and '+:=' are equivalent alternates for
           direct concatenation; '+=:' is NOT a documented form and should not be confused with them.
SEVERITY : AMBIGUITY
NOTE     : Both forms are canonical and accepted; they are provided to cater to user preference.

ISSUE 6 [DONE]
----------------------------------------------------------------------------------------------------

ISSUE    : The manual says "These 'once' variations are executed independently from the normal
           variations" but does not state what scope "once" applies to -- per-file, per-include
           site, or globally for the whole compilation.
CORRECT  : The runtime tracks included file paths in a single '_onceList' that lives on the
           object responsible for the entire compilation run.  It is populated on the first
           successful load of a library path and checked before every subsequent load attempt.
           Therefore "once" means ONCE PER ENTIRE COMPILATION -- across the main JxMakeFile
           and all files it includes recursively, for the whole execution of jxmake.
           An additional implementation detail worth documenting: the 'once' list stores the
           RESOLVED ABSOLUTE path of the library file, not the raw argument string.  Two
           different argument strings that resolve to the same file will therefore be treated
           as the same include for '_once' purposes.
           The manual note about "executed independently from the normal variations" means that
           ':::include_once' and ':::include' each have their own separate tracking; calling
           ':::include' for a file does NOT prevent ':::include_once' from loading it on its
           first invocation, and vice versa.
           The manual should be updated to state these three things explicitly:
             1. The 'once' guard applies globally for the entire compilation run.
             2. Tracking is by resolved absolute path.
             3. The 'once' and non-once variants track independently of each other.
SEVERITY : AMBIGUITY

ISSUE 7 [DONE]
----------------------------------------------------------------------------------------------------

FILE     : docs/txt/en_US/07-Built-In-Functions.txt
LOCATION : Section "Function call shortcuts for '$partn' and '$partnm'" -- note about double-quoted
           strings
ISSUE    : The manual states the '$partn' and '$partnm' shortcuts "will not be evaluated when
           placed inside double-quoted strings."  However, it also states (in the path shortcuts
           section): "unlike calling functions from within double-quoted strings which is not
           supported, using those [path] shortcuts from inside double-quoted strings is actually
           supported and evaluated."  This creates a two-tier rule with no unified statement.
           A reader must visit two separate sections to understand the complete picture.
CORRECT  : The rule governing what is and is not evaluated inside a plain double-quoted string
           ("...") should be stated once, clearly, and each relevant section should cross-reference
           it.  The complete rule, drawn from all relevant sections, is:

               INSIDE a plain double-quoted string "...":
               - Variable evaluations '${V}' and '$[V]'          ARE evaluated.
               - Standard function calls '$func(...)'             are NOT evaluated (plain text).
               - Path shortcuts '~${V}', '^${V}', '-${V}'        ARE evaluated.
               - partn/partnm shortcuts '${V}<n>'                 are NOT evaluated (plain text).
               - stack shortcuts '{{ ... }}'                      are NOT evaluated (plain text).
               - set creation operator '{ ... }'                  are NOT evaluated (plain text).

               SEPARATE term forms (not used inside "..."; they replace it):
               - The combining  operator ."..." is a standalone term.
                 Evaluation: ALWAYS LAZY regardless of '=' vs ':='.
                 Members: combined into one member on each evaluation.
               - The flattening operator :"..." is a standalone term.
                 Evaluation: ALWAYS DIRECT regardless of '=' vs ':='.
                 Members: flattened into one member, frozen at assignment time.

               The key distinction confirmed by runtime behaviour:
                 A = 10 ; B = 11
                 C = ."${A} ${B}"   (* lazy  -- tracks A,B; prints '20 11' after A=20 *)
                 D = :"${A} ${B}"   (* direct -- frozen; still prints '10 11' after A=20 *)
SEVERITY : INCONSISTENCY

ISSUE 8 [DONE]
----------------------------------------------------------------------------------------------------

FILE     : docs/txt/en_US/07-Built-In-Functions.txt
LOCATION : Near the set creation operator '{ }' description
ISSUE    : The manual states "DO NOT separate the terms within it using ','." but does not
           explain WHY or what actually happens if you do.  A programmer may read this as a
           style suggestion rather than a semantic rule.  The manual immediately contrasts
           '{ }' with '{{ }}' which DOES use commas, making the distinction easy to miss.
CORRECT  : A comma inside '{ }' is NOT a separator -- it is treated as a literal bare-word
           token and becomes its own set member.  Confirmed by runtime:

               echoln $part_count({ A B C })    # prints 3
               echoln $part_count({ A, B, C })  # prints 5  (commas are members)

           So '{ A, B, C }' produces 5 members: A  ,  B  ,  C  -- the two commas are
           extra string members with value ','.

           The manual should replace "DO NOT separate the terms within it using ','" with
           an explicit statement of the consequence:
               "Commas inside '{ }' are treated as literal set members, not separators.
                '{ A, B, C }' produces 5 members, not 3.  Use spaces only."

           The contrast with '{{ }}' (where commas ARE separators) should also be made
           explicit in a side-by-side note.
SEVERITY : AMBIGUITY

FILE     : docs/txt/en_US/08-User-Defined-Function.txt
LOCATION : Section "User-Defined Function" -- NOTE on $call vs $exec restrictions
ISSUE    : The manual states "A user-defined function called using 'exec' contains commands to
           be executed by the shell/operating system and cannot call other functions."  The
           phrasing "cannot call other functions" is correct as a runtime rule, but the manual
           does not clarify WHERE in the function body the restriction applies, nor does it
           explain that other JxMake statements (assignments, if blocks, loops, local variables)
           ARE permitted freely inside an 'exec' function body.  A reader may interpret "cannot
           call other functions" as meaning the entire function body is restricted to '@' lines.
CORRECT  : The runtime enforces this rule: an '$exec' function that calls '$call' or '$exec'
           anywhere in its body -- even outside of '@' lines -- raises a runtime error:
               "RUNTIME ERROR: a user-defined function called using '$exec()' is not allowed
                to call other user-defined functions"
           The manual's core restriction is therefore accurate.  What is missing is the
           clarification that non-function JxMake statements (assignment, if, loop, etc.)
           ARE permitted inside an 'exec' function body, and that the ban is specifically on
           '$call' and '$exec' invocations.  The manual should add:
               "Note that assignment statements, conditionals, loops, and other JxMake
                statements are permitted inside an 'exec' function.  Only invocations of
                user-defined functions via '$call' or '$exec' are prohibited."
SEVERITY : AMBIGUITY
