Task: Create a single compact, AI-optimized reference document for the JxMake
scripting language by combining and compacting the following source files:

- docs/txt/JxMake-Grammar.txt (formal EBNF grammar)
- docs/txt/en_US/01-Introduction.txt
- docs/txt/en_US/02-Defining-Strings.txt
- docs/txt/en_US/03-Defining-Dependency-List.txt
- docs/txt/en_US/04-Defining-Variables.txt
- docs/txt/en_US/05-Special-Variables.txt
- docs/txt/en_US/06-Regular-Expression-In-Variable.txt
- docs/txt/en_US/07-Built-In-Functions.txt
- docs/txt/en_US/08-User-Defined-Function.txt
- docs/txt/en_US/09-Targets.txt
- docs/txt/en_US/10-Flow-Control.txt
- docs/txt/en_US/11-Loop.txt
- docs/txt/en_US/12-Numerical-Operations.txt
- docs/txt/en_US/13-Loadable-Libraries.txt
- docs/txt/en_US/14-Simple-Programmer-Hardware.txt
- docs/txt/en_US/99-Appendix-X_Built-In-Function-Parameters.txt (parameter
  schemas only — see rule 2 below)

Explicitly EXCLUDE:
- docs/txt/en_US/00-System-Configuration.txt (font/env-setup instructions,
  not grammar-relevant)
- docs/txt/en_US/99-Appendix-A_*, 99-Appendix-B_*, 99-Appendix-C_* (hardware
  pinout ASCII diagrams — not grammar or function-parameter content)

Output file: docs/txt/JxMake-AI-Reference.txt

Goal: after reading ONLY this one output file, an LLM should be able to
correctly write and reason about JxMake scripts, including calling every
built-in function with correct arguments/defaults/behavior and correctly
constructing any JSON-shaped parameters — without needing the 16 source files.

Hard requirements:

1. Zero loss of semantic/behavioral information. Every function's
   parameters, types, default values, valid enum values, error/throw
   conditions, and behavioral notes (e.g. "throws if not found unless
   global_fb=true") must be preserved. Only cut: alignment whitespace/
   padding, restated boilerplate phrasing, and duplicate explanations.

2. For JSON-shaped parameters (e.g. $fwc_load_elf_bin's [is_rule]/
   [es_rule]), preserve the schema itself (field names, types, semantics,
   defaults, enum values) in compact form, but do NOT include the full
   worked example JSON blocks from 99-Appendix-X. Replace each with a
   one-line pointer, e.g.:
     "full example: docs/txt/en_US/99-Appendix-X_Built-In-Function-Parameters.txt § <section>"
   Rationale: the tool can emit/validate this JSON at runtime, and the
   appendix stays available for an AI to re-read on demand — no need to
   duplicate full examples in the compact reference.

3. Grammar section: keep the EBNF rules complete and exact (they're the
   ground truth for parsing, including every [WS-*] whitespace-convention
   annotation — these are routinely load-bearing for correctness). Compact
   only the surrounding prose/comments into terse single-line annotations.

4. Pick ONE compact, consistent notation up front (e.g. a terse
   `$name(arg:type[=default], [opt:type=default]) -> ret_type  # notes`
   style) and use it uniformly for every one of the ~470 built-in
   functions and every grammar rule. Do not let the format drift partway
   through the document.

5. Preserve the existing logical grouping/order of topics and functions
   from the source files, so the compacted file stays easy to diff
   against source mentally.

6. This file WILL be extended/updated later as source .txt files change. To make
   that safe and mechanical:
   - At the top of the output file, include a "SOURCE INVENTORY" table listing
     every source file used, with its line count and byte size at the time of
     this generation, e.g.:
       docs/txt/JxMake-Grammar.txt                              1189 lines  62933 bytes
       docs/txt/en_US/07-Built-In-Functions.txt                  935 lines  82234 bytes
       ...
     This lets a future session run `wc -lc` on each source file and instantly
     see which ones drifted from what this reference reflects, even if the
     user doesn't remember to list all of them.
   - Include a short "UPDATE PROCEDURE" note in the header, addressed to a
     future AI session, e.g.: "When told a source file changed: re-read that
     file, diff its content against what this reference currently reflects,
     add/update/remove only the affected entries using the per-entry template
     below, leave all unrelated entries untouched, then update that file's row
     in the SOURCE INVENTORY table above to the new line count/byte size."
   - Document the one canonical per-function entry template explicitly, so
     updates follow the same format as the original generation.

7. When done, report: final byte size of the output file, combined byte
   size of the 16 source files, and % reduction. Also spot-check ~5
   functions at random (including at least one with a JSON parameter)
   against the source to confirm defaults, types, and behavior notes all
   survived intact.

8. Do not fabricate or infer any function/parameter not present in the
   source files. This is a reference artifact, not prose documentation —
   no added commentary or opinion.
