====================================================================================================
WindowsDriverInstaller_FFM.java - Win32 API / Native Structure Reference
====================================================================================================

Internal engineering reference. Not a Microsoft document and not a substitute for the Windows SDK.
It exists to help a future maintainer of this class read the FFM (Java Foreign Function & Memory
API) bindings without having to re-derive every struct offset and calling convention from scratch.

Everything below describes what THIS FILE actually does - the field layouts, flag values, and
calling sequences match the static block and the various `_elevated*`/`_signCatalog` helper methods
in WindowsDriverInstaller_FFM.java as of the version this document was written against. Where a
detail was confirmed against Microsoft's own reference pages, it is marked VERIFIED with a Source:
line. Where something instead has to be reconstructed because Microsoft does not document it, it is
marked RECONSTRUCTED / INFERRED, and the reasoning is spelled out so a future reader can judge how
much to trust it.

Some Source: URLs below (Microsoft Learn API reference pages in particular) may prompt for Microsoft
account sign-in when opened directly in a browser, even though the underlying page is public
reference documentation. This does not affect how those facts were verified - it only means a reader
following the link by hand may hit a sign-in prompt.

No third-party source code is reproduced or excerpted anywhere in this file.

FFM conventions used throughout this file:

  DW  = ValueLayout.JAVA_INT : used for DWORD, BOOL, LONG, HRESULT, ALG_ID - all 32-bit on Win32,
                               regardless of the process being x64; Win32 kept these types 32-bit
                               for ABI compatibility reasons unrelated to pointer width

  PTR = ValueLayout.ADDRESS  : used for every HANDLE, HWND, HKEY, HCERTSTORE, LP*, or
                               output-by-reference parameter

All downcalls are bound through the private `_bind(linker, lib, name, fd)` helper, which does
`linker.downcallHandle(lib.find(name).orElseThrow(...), fd)` - i.e. a plain default-convention
downcall handle for each symbol, no critical/trivial linker options are used.

DISCLAIMER:
    Nothing in this file is copied or paraphrased from Microsoft's text - every description below is
    written from scratch, using the SDK reference pages only to check facts (function/struct member
    existence, order, size, and behavior), not as source text. All structure layouts, field offsets,
    sizes, and alignments described here were independently derived and/or verified against public
    Windows SDK headers and Microsoft Learn documentation.


====================================================================================================
SECTION A - Process / Elevation Layer (Kernel32.dll, Shell32.dll)
====================================================================================================

This layer exists because two operations later in the file (certificate creation/trust and catalog
signing) need an elevated token, and the only way this FFM backend can get one is to relaunch its
own JVM through ShellExecuteExW with lpVerb="runas" and wait on the resulting process handle.

CreateFileW/CloseHandle appear again in Section D (used to open the INF file for hashing), not just
here.

----------------------------------------------------------------------------------------------------
CreateFileW
----------------------------------------------------------------------------------------------------
Source             : https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew

DLL                : Kernel32.dll
Header             : fileapi.h
Calling convention : __stdcall (all Win32 API calls in this document use the standard Win32 calling
                     convention; the FFM Linker's default downcall convention on Windows already
                     matches this, so no explicit convention option is passed)

Parameters         : lpFileName (LPCWSTR), dwDesiredAccess (DWORD), dwShareMode (DWORD),
                     lpSecurityAttributes (LPSECURITY_ATTRIBUTES, optional), dwCreationDisposition
                     (DWORD), dwFlagsAndAttributes (DWORD), hTemplateFile (HANDLE, optional)
Return value       : HANDLE to the opened file, or INVALID_HANDLE_VALUE (-1 as a pointer-sized
                     value) on failure.
Purpose            : General-purpose file/device open call. This class uses only the
                     read-a-file-that-already-exists path.

FFM notes          : `FunctionDescriptor.of(PTR, PTR, DW, DW, PTR, DW, DW, PTR)` - 7 parameters,
                     matches the prototype above 1:1. Used once, in `_elevatedCreateAndSignCatalog`,
                     to open the INF file for GENERIC_READ/FILE_SHARE_READ/OPEN_EXISTING so its
                     bytes can be hashed via CryptCATAdminCalcHashFromFileHandle2. The returned
                     handle is compared against -1L (INVALID_HANDLE_VALUE) via `hInfFile.address()
                     == INVALID_HANDLE_VALUE`, and is always closed in a `finally` block.

GetLastError
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-getlasterror

DLL          : Kernel32.dll
Header       : errhandlingapi.h

Parameters   : none
Return value : DWORD, the calling thread's last-error code.
Purpose      : Standard Win32 extended-error retrieval, read immediately after a Win32 call reports
               failure.

FFM notes    : `FunctionDescriptor.of(DW)`. Wrapped by the private `_lastError()` helper (`(int)
               _GetLastError.invoke()`), called from nearly every failure branch in this file to
               enrich the returned log/message. Caveat worth flagging for a future maintainer:
               GetLastError's value is only meaningful immediately after the failing call, on the
               same thread, before any other Win32 call runs - the code here is careful to call it
               right after each checked API, which is correct, but any future refactor that reorders
               these calls (e.g. moving logging after other cleanup calls) would silently corrupt
               the reported error code.

WaitForSingleObject
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject

DLL          : Kernel32.dll
Header       : synchapi.h

Parameters   : hHandle (HANDLE), dwMilliseconds (DWORD)
Return value : DWORD - WAIT_OBJECT_0 (0) on signal, WAIT_TIMEOUT (0x102) on timeout, WAIT_FAILED on
               error.
Purpose      : Blocks the calling thread until the given kernel object (here, always a process
               handle) becomes signaled or the timeout elapses.

FFM notes    : `FunctionDescriptor.of(DW, PTR, DW)`. Used in `_shellExecuteElevatedAndWait` to wait
               for the elevated child process, with the timeout computed as `waitTimeMinutes *
               60_000`. The returned code is compared against the local constant `WAIT_TIMEOUT =
               0x102`; on timeout the code calls TerminateProcess and reports RETCODE_TIMEOUT.

GetExitCodeProcess
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess

DLL          : Kernel32.dll
Header       : processthreadsapi.h

Parameters   : hProcess (HANDLE), lpExitCode (LPDWORD, out)
Return value : BOOL
Purpose      : Reads back the exit code of a (by then already-signaled) process.

FFM notes    : `FunctionDescriptor.of(DW, PTR, PTR)`. Called right after WaitForSingleObject returns
               non-timeout; the exit code buffer is a 4-byte arena allocation read back with
               `exitCodeOut.get(ValueLayout.JAVA_INT, 0)`. This exit code becomes the returned
               XCom.Pair's first element, i.e. the elevated child's own `System.exit(exitCode)`
               value from `main()` flows all the way back to the un-elevated caller through this
               path.

TerminateProcess
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess

DLL          : Kernel32.dll
Header       : processthreadsapi.h

Parameters   : hProcess (HANDLE), uExitCode (UINT)
Return value : BOOL
Purpose      : Forcibly ends a process; here used only as a timeout backstop.

FFM notes    : `FunctionDescriptor.of(DW, PTR, DW)`. Only reached on the WAIT_TIMEOUT branch, called

               directly to returning RETCODE_TIMEOUT, so termination is best-effort/fire-and-forget

LocalFree
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-localfree

DLL          : Kernel32.dll
Header       : winbase.h

Parameters   : hMem (HLOCAL)
Return value : HLOCAL (NULL on success, unlike most BOOL-returning Win32 calls)
Purpose      : Frees memory that Crypt32 allocated on the caller's behalf via the
               CRYPT_ENCODE_ALLOC_FLAG convention (see CryptEncodeObjectEx below).

FFM notes    : `FunctionDescriptor.of(PTR, PTR)` - return type is PTR (not DW) because LocalFree
               returns a handle, not a BOOL; the return value is discarded at every call site in
               this file. Called on `ekuEncoded` (Section B) and `spcLinkEnc` (Section D), each in a
               `finally` block matching the CryptEncodeObjectEx call that produced it. Ownership
               rule: any buffer that CryptEncodeObjectEx returned via its out-pointer with
               CRYPT_ENCODE_ALLOC_FLAG set was allocated by Crypt32's internal allocator and must be
               released with LocalFree, never freed by any other means and never left for the arena
               to reclaim (the arena did not allocate it).

ShellExecuteExW
----------------------------------------------------------------------------------------------------
Source             : https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecuteexw

DLL                : Shell32.dll
Header             : shellapi.h
Calling convention : __stdcall

Parameters         : pExecInfo (SHELLEXECUTEINFOW *, in/out - the struct is both filled in by the
                     caller and partially filled in by the function, notably hProcess and hInstApp)
Return value       : BOOL (TRUE on success; call GetLastError on FALSE)
Purpose            : Launches a file/verb combination through the shell rather than through
                     CreateProcess directly. This is what makes UAC elevation possible from user
                     code: passing lpVerb="runas" tells the shell to invoke the "Run as
                     administrator" activation path (an elevated COM moniker under the hood), which
                     CreateProcess itself cannot do.

FFM notes          : `FunctionDescriptor.of(DW, PTR)` - single parameter, the struct pointer. Called
                     exactly once per elevated operation, from `_shellExecuteElevatedAndWait`.
                     GetLastError()==1223 (ERROR_CANCELLED) after a FALSE return is treated
                     specially and mapped to RETCODE_UAC_DECLINED, distinguishing "user clicked No
                     on the UAC prompt" from every other failure mode.

Windows-specific caveats relevant to this implementation:
    - Because SEE_MASK_NOCLOSEPROCESS is set, the returned hProcess handle is the caller's
      responsibility to close (done in a `finally` in `_shellExecuteElevatedAndWait`).
    - lpDirectory is explicitly set to the parent's `user.dir` because an elevated child's working
      directory is not guaranteed to match the parent's; this matters here because the launched
      command line embeds a (resolved-to-absolute, per `_absoluteClassPath()`) classpath, but if any
      other relative path were ever added to the command line it would resolve against lpDirectory,
      not the parent's cwd, unless lpDirectory is set correctly - which this code already does.
    - Microsoft's own documentation notes COM should be initialized before calling ShellExecuteEx
      for certain shell extensions; this code does not call CoInitializeEx before invoking it. This
      has not caused an observed failure with the "runas" verb specifically (which does not go
      through arbitrary shell extensions), but it is a latent gap relative to Microsoft's documented
      best practice if the verb or target ever changes.

STRUCTURE: SHELLEXECUTEINFOW
----------------------------------------------------------------------------------------------------
Source             : https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow
                     (struct member list cross-checked against the ShellExecuteExW page above; also
                     generally well-known, stable Win32 struct).

Fields             : Field byte offsets, as hardcoded in the SEI_* constants in this file:
                         cbSize(0,DWORD) fMask(4,DWORD) hwnd(8,HWND) lpVerb(16,LPCWSTR)
                         lpFile(24,LPCWSTR) lpParameters(32,LPCWSTR) lpDirectory(40,LPCWSTR)
                         nShow(48,int) hInstApp(56,HINSTANCE) lpIDList(64,void*) lpClass(72,LPCWSTR)
                         hkeyClass(80,HKEY) dwHotKey(88,DWORD) hIcon/hMonitor(96,HANDLE)
                         hProcess(104,HANDLE)
Size               : 112 bytes, 8-byte aligned (x64).
Purpose            : Describes a shell "verb" invocation (e.g. "open", "runas") plus the
                     file/parameters/window-state to launch it with, and receives back a process
                     handle and a pseudo-HINSTANCE result code.

FFM notes          : Built by hand in `_shellExecuteElevatedAndWait` via `arena.allocate(SEI_SIZE,
                     8)` and explicit `.set(...)` calls at each SEI_* offset - there is no reusable
                     "StructLayout" object, just raw offsets, which is why the comment block above
                     the SEI_* constants exists as the canonical description of the layout. fMask is
                     set to SEE_MASK_NOCLOSEPROCESS(0x40) | SEE_MASK_NOASYNC(0x100); nShow is
                     SW_HIDE(0); lpVerb is always the literal "runas".

Ownership/lifetime : All the LPCWSTR fields point into the same `Arena .ofConfined()` used for the
                     rest of the call, so they stay valid for the whole synchronous ShellExecuteExW
                     + WaitForSingleObject + GetExitCodeProcess sequence and are freed automatically
                     when the try-with-resources arena closes - no manual cleanup needed for the
                     strings themselves. hProcess, once received back into the struct, is a real
                     kernel handle and IS the caller's responsibility (see CloseHandle above) - it
                     is not implicitly cleaned up by the arena.


====================================================================================================
SECTION B - Certificate Store / Self-Signed Certificate Layer (Crypt32.dll)
====================================================================================================

This section covers everything used to check for/create/trust the self-signed code-signing
certificate this tool generates. Two operating system certificate stores are relevant throughout:
the per-machine "Root"/"TrustedPublisher" stores (which is what actually makes Windows trust a
driver signed with this certificate) and the per-user "My" store (which is where the certificate's
private-key linkage lives so it can be used later to sign the catalog).

----------------------------------------------------------------------------------------------------
CertOpenStore
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certopenstore

DLL          : Crypt32.dll
Header       : wincrypt.h

Parameters   : lpszStoreProvider, dwMsgAndCertEncodingType (DWORD), hCryptProv (optional, unused
               here -> 0), dwFlags (DWORD), pvPara (provider-specific, here a store name)
Return value : HCERTSTORE, or NULL on failure.
Purpose      : Opens (or implicitly creates) a certificate store of a given provider type at a given
               scope (machine vs. user) and name.

FFM notes    : `FunctionDescriptor.of(PTR, PTR, DW, PTR, DW, PTR)`. The first parameter
               (lpszStoreProvider) is passed as `_handleOf(CERT_STORE_PROV_SYSTEM_W)` where
               CERT_STORE_PROV_SYSTEM_W = 10L - this is one of the "predefined, small-integer store
               provider" values that wincrypt.h expects to be passed by value in the pointer-typed
               parameter slot rather than as a real string pointer (a well-known, if unusual, Win32
               ABI convention also used for several other "or provide LPCSTR" parameters in this API
               family). Wrapped by the private `_certStoreOpen(arena, locationFlag, storeName)`
               helper used throughout the rest of this file. Called with
               CERT_SYSTEM_STORE_LOCAL_MACHINE for "Root"/"TrustedPublisher" and
               CERT_SYSTEM_STORE_CURRENT_USER for "My".

CertFindCertificateInStore
----------------------------------------------------------------------------------------------------
Source             : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certfindcertificateinstore

DLL                : Crypt32.dll
Header             : wincrypt.h

Parameters         : hCertStore (HCERTSTORE), dwCertEncodingType (DWORD), dwFindFlags (DWORD, always
                     0 here), dwFindType (DWORD), pvFindPara (find-type-specific), pPrevCertContext
                     (optional, always NULL here - meaning "start search from the beginning")
Return value       : PCCERT_CONTEXT matching the search, or NULL if none found.
Purpose            : Iterative certificate-store search primitive; used here in its simplest form
                     (single call, no continuation) to check whether a certificate with a given
                     subject substring already exists.

FFM notes          : `FunctionDescriptor.of(PTR, PTR, DW, DW, DW, PTR, PTR)` - 7 slots: 1 return
                     type (PTR/PCCERT_CONTEXT) followed by 6 argument layouts, one per parameter
                     listed above. dwFindType is always the module constant CERT_FIND_SUBJECT_STR_W
                     = (8 << 16) | 7 (the standard encoding of CERT_COMPARE_NAME_STR_W shifted by
                     CERT_COMPARE_SHIFT, OR'd with CERT_INFO_SUBJECT_FLAG - a well-documented but
                     easy-to-miscount bit pattern, worth double-checking against wincrypt.h if this
                     value is ever touched). Used in `isProviderAlreadyTrusted` (search by provider
                     name across "Root"/"TrustedPublisher") and in `_elevatedCreateAndSignCatalog`
                     (locate the signing cert in CurrentUser\My by provider name before calling
                     `_signCatalog`).

Ownership/lifetime : every non-NULL PCCERT_CONTEXT this returns MUST be released with
                     CertFreeCertificateContext exactly once by the caller, independent of the store
                     it came from - the code does this consistently, either immediately
                     (isProviderAlreadyTrusted) or via a `finally` around the `_signCatalog` call.

CertStrToNameW
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certstrtonamew

DLL          : Crypt32.dll
Header       : wincrypt.h

Parameters   : dwCertEncodingType (DWORD), pszX500 (LPCWSTR), dwStrType (DWORD), pvReserved (must be
               NULL), pbEncoded (BYTE*, out, may be NULL to query size), pcbEncoded (DWORD*,
               in/out), ppszError (LPCWSTR*, optional out)
Return value : BOOL
Purpose      : Parses a human-readable X.500 distinguished-name string (e.g. "CN=Some Publisher")
               into its DER-encoded form, the format CertCreateSelfSignCertificate's subject
               parameter requires.

FFM notes    : `FunctionDescriptor.of(DW, DW, PTR, DW, PTR, PTR, PTR, PTR)` - 7 inputs. Called twice
               in `_elevatedCreateAndTrustProvider`, following the standard Win32 "size then fill"
               two-pass pattern: first with pbEncoded=NULL to learn the required buffer size via
               pcbEncoded, then again with a freshly allocated buffer of that size. dwStrType is
               always CERT_X500_NAME_STR(3); dwCertEncodingType is X509_ASN_ENCODING(1). ppszError
               is always MemorySegment.NULL - this code does not currently retrieve the detailed
               "which character was invalid" diagnostic CertStrToNameW can optionally provide, it
               only checks GetLastError.
FFM caveat   : because both calls read the SAME `subjectStr`/`cbSubject` MemorySegments, and the
               second call's output buffer is sized exactly from the first call's reported length,
               this pattern is correct but fragile - anyone changing the subject string encoding
               without re-running the sizing call would silently truncate.

----------------------------------------------------------------------------------------------------
CertCreateSelfSignCertificate
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certcreateselfsigncertificate

DLL          : Crypt32.dll
Header       : wincrypt.h

Parameters   : hCryptProvOrNCryptKey (HCRYPTPROV_OR_NCRYPT_KEY_HANDLE, optional), pSubjectIssuerBlob
               (PCERT_NAME_BLOB), dwFlags (DWORD), pKeyProvInfo (PCRYPT_KEY_PROV_INFO, optional),
               pSignatureAlgorithm (PCRYPT_ALGORITHM_IDENTIFIER, optional), pStartTime (PSYSTEMTIME,
               optional), pEndTime (PSYSTEMTIME, optional), pExtensions (PCERT_EXTENSIONS, optional)
Return value : PCCERT_CONTEXT for the newly built certificate, or NULL.
Purpose      : Builds an in-memory, self-signed X.509 certificate from a subject name, a private key
               handle, and an optional extension list - no certificate authority or network
               round-trip involved, which is exactly why this tool can produce a usable code-signing
               certificate entirely offline.

FFM notes    : `FunctionDescriptor.of(PTR, PTR, PTR, DW, PTR, PTR, PTR, PTR, PTR)` - 9 slots: 1
               return type (PTR/PCCERT_CONTEXT) followed by 8 argument layouts, one per parameter
               listed above. Called with:
               hCryptProvOrNCryptKey = the NCrypt key handle from Section C (hKey);
               pSubjectIssuerBlob = the CertStrToNameW-encoded "CN=<providerName>" blob; dwFlags = 0
               (neither CERT_CREATE_SELFSIGN_NO_KEY_INFO nor _NO_SIGN is set - the default behavior,
               i.e. the certificate IS signed and DOES carry a CERT_KEY_PROV_INFO_PROP_ID pointing
               back at the CNG key container); pKeyProvInfo = the hand-built CRYPT_KEY_PROV_INFO
               (Section B structures below); pSignatureAlgorithm = an explicit SHA256RSA OID (see
               caveat below); start/end time = NULL, NULL (defaults to "now" through "now + 1
               year"); pExtensions = the Enhanced Key Usage extension array built earlier in the
               same method.

Windows-specific behavior relevant to this implementation:
    If pSignatureAlgorithm were left NULL, Microsoft's own reference documents that the function
    defaults to SHA1RSA. This class deliberately never relies on that default - it always supplies
    an explicit SHA256RSA CRYPT_ALGORITHM_IDENTIFIER, because every other hashing step in this file
    (the catalog's own SIP digest, the SIGNER_SIGNATURE_INFO.algidHash used later) is likewise
    pinned to SHA-256, and an inconsistently-hashed certificate would be an easy and hard-to-notice
    source of a rejected signature. There is also a documented leap-day caveat around the
    auto-computed pEndTime (a certificate created without an explicit pEndTime on Feb 29 can trip on
    the "add one year" math); this code does not special-case that, since it always uses the default
    +1-year window and a certificate created on a leap day is an edge case rare enough it has not
    been addressed here - worth knowing about, not yet fixed.

CertAddCertificateContextToStore
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certaddcertificatecontexttostore

DLL          : Crypt32.dll
Header       : wincrypt.h

Parameters   : hCertStore (HCERTSTORE), pCertContext (PCCERT_CONTEXT), dwAddDisposition (DWORD),
               ppStoreContext (PCCERT_CONTEXT*, optional out - always NULL here)
Return value : BOOL
Purpose      : Copies a certificate context into a store (system stores in this case), optionally
               replacing an existing entry with the same identity.

FFM notes    : `FunctionDescriptor.of(DW, PTR, PTR, DW, PTR)`. dwAddDisposition is always
               CERT_STORE_ADD_REPLACE_EXISTING(3), so re-running the trust step is idempotent rather
               than erroring on "already present". Called three times per successful trust
               operation: once against CurrentUser\My (so the private-key-linked certificate itself
               is discoverable there later by CertFindCertificateInStore) and once each against
               LocalMachine\Root and LocalMachine\TrustedPublisher (which is the pair of stores that
               actually makes Windows treat a driver signed with this certificate as trusted, per
               standard Authenticode trust rules - Root establishes the certificate as a trust
               anchor, and TrustedPublisher marks it as an explicitly trusted publisher without
               which most driver-signature UI still warns).

CertGetCertificateContextProperty
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatecontextproperty

DLL          : Crypt32.dll
Header       : wincrypt.h

Parameters   : pCertContext (PCCERT_CONTEXT), dwPropId (DWORD), pvData (void*, out - NULL to query
               size only, as used here), pcbData (DWORD*, in/out size)
Return value : BOOL
Purpose      : Reads a named property off a certificate context. Used here purely as a presence
               probe: dwPropId = CERT_KEY_PROV_INFO_PROP_ID(2), pvData = NULL, so a nonzero return

               context's properties into the store's copy, but this had not been directly confirmed
               for this exact code path, hence the check - see the "SignerSignEx2/SignerSignEx3
               E_INVALIDARG" troubleshooting note below for why this matters.

CryptAcquireCertificatePrivateKey
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptacquirecertificateprivatekey

DLL          : Crypt32.dll
Header       : wincrypt.h

Parameters   : pCert (PCCERT_CONTEXT), dwFlags (DWORD), pvReserved (void*, always NULL here),
               phCryptProvOrNCryptKey (HCRYPTPROV_OR_NCRYPT_KEY_HANDLE*, out), pdwKeySpec (DWORD*,
               out), pfCallerFreeProvOrNCryptKey (BOOL*, out)
Return value : BOOL
Purpose      : Retrieves a handle to a certificate's associated private key, reading the
               CERT_KEY_PROV_INFO_PROP_ID property to decide whether to open it via NCrypt (CNG) or
               legacy CryptAcquireContext. This is the exact function SignerSignEx is understood to

FFM notes    : `FunctionDescriptor.of(DW, PTR, DW, PTR, PTR, PTR, PTR)` - 6 inputs. Added as a

               whether private-key acquisition itself succeeds independent of whatever SignerSignEx
               does afterward - see the "Investigation history" note below. If callerFree comes back
               true and the returned dwKeySpec is CERT_NCRYPT_KEY_SPEC, the handle is freed via
               NCryptFreeObject; this backend's own certificates are now provisioned entirely via legacy
               CryptoAPI (see CryptAcquireContextW/CryptGenKey below), so that branch is not expected to
               fire in practice, but is kept since this function can in general hand back either kind of
               key.

----------------------------------------------------------------------------------------------------
CryptEncodeObjectEx
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptencodeobjectex

====================================================================================================
SECTION C - Private Key Provisioning Layer (Advapi32.dll, Ncrypt.dll)
====================================================================================================

This section creates the actual RSA private key the self-signed certificate is built around, using
the legacy CryptoAPI (CAPI1) provider/key model (CryptAcquireContextW/CryptGenKey) rather than the
modern Cryptography API: Next Generation (CNG) key-storage API. CNG was tried first, since Microsoft
recommends it for new code, but had to be abandoned - see the "Investigation history" note in
SECTION E below: SignerSignEx's internal CryptAcquireCertificatePrivateKey call only follows the
legacy CryptAcquireContext path unless given an NCrypt-allowing flag, which it is not, so a
CNG-provisioned key is unusable by this backend's signing step regardless of how correctly
CRYPT_KEY_PROV_INFO otherwise describes it. NCryptFreeObject (last entry below) remains bound only
because SECTION E's diagnostic can in general still observe a CNG key handle back from
CryptAcquireCertificatePrivateKey.

CryptAcquireContextW
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptacquirecontextw

DLL          : Advapi32.dll
Header       : wincrypt.h

Parameters   : phProv (HCRYPTPROV*, out), pszContainer (LPCWSTR, key container name), pszProvider
               (LPCWSTR, optional - NULL selects the default RSA Full CSP), dwProvType (DWORD),
               dwFlags (DWORD)
Return value : BOOL
Purpose      : Acquires a handle to a legacy CryptoAPI (CAPI1) key container, creating it first if
               CRYPT_NEWKEYSET is set. This backend uses it (with PROV_RSA_FULL and a fresh randomly

               key.

               new, CRYPT_NEWKEYSET is always correct - there is never an existing container to reopen.

====================================================================================================
SECTION D - Catalog Building Layer (Wintrust.dll)
====================================================================================================

This section builds a v2 security catalog (.cat file) for the INF, the mechanism Windows driver
installation uses to verify the INF's integrity without requiring the INF itself to be
embedded-signed (INF files cannot carry an Authenticode signature the way a PE file can - a catalog
is the standard indirection Microsoft designed for exactly this case).

----------------------------------------------------------------------------------------------------
CryptCATAdminAcquireContext2
----------------------------------------------------------------------------------------------------
Source       : https://learn.microsoft.com/en-us/windows/win32/api/mscat/nf-mscat-cryptcatadminacquirecontext2

DLL          : Wintrust.dll
Header       : mscat.h

Parameters   : phCatAdmin (HCATADMIN*, out), pgSubsystem (const GUID*), pwszHashAlgorithm (LPCWSTR,
               optional), pStrongHashPolicy (PCCERT_STRONG_SIGN_PARA, optional), dwFlags (DWORD)
Return value : BOOL
Purpose      : Acquires a catalog-administration context scoped to a given "subsystem" GUID (which
               SIP/verification family the catalog is for) and hash algorithm - required before any
               other CryptCATAdmin*/ CryptCAT* call in this family can be used.

FFM notes    : `FunctionDescriptor.of(DW, PTR, PTR, PTR, PTR, DW)`. pgSubsystem is always the
               DRIVER_ACTION_VERIFY GUID (see the GUID structure entry below) - this scopes the
               whole catalog to the driver installation verification subsystem, matching what
               pnputil/the Device Installer actually validates against later. pwszHashAlgorithm is
               always "SHA256" (matching the SHA-256 hash used consistently throughout the file, and
               matching what WindowsDriverInstaller_PS1's New-FileCatalog defaults to as well, so
               both backends produce catalogs hashed the same way). pStrongHashPolicy and dwFlags
               are NULL/0 (no extra policy enforcement requested).

====================================================================================================
SECTION E - Authenticode Signing Layer (Mssign32.dll)
====================================================================================================

This is the layer that actually applies a digital signature to the finished .cat file, using the
certificate/key built in Sections B/C. Everything in this section is built from Microsoft Learn
"conceptual" reference pages rather than a header file - Microsoft explicitly documents these
functions and structures on learn.microsoft.com, but (per Microsoft's own notes on those pages) does
not ship a header declaring them; a caller is expected to declare the prototypes itself and
dynamically resolve the DLL export, which is exactly the pattern this file follows via SymbolLookup
instead of LoadLibrary/GetProcAddress.

----------------------------------------------------------------------------------------------------
SignerSignEx
----------------------------------------------------------------------------------------------------
Source             : https://learn.microsoft.com/en-us/windows/win32/seccrypto/signersignex

DLL                : Mssign32.dll
Header             : none (explicitly undeclared by Microsoft; see above)
Calling convention : WINAPI (__stdcall) Parameters (9, in the exact order below - VERIFIED against
                     Microsoft Learn): dwFlags (DWORD, in), pSubjectInfo (SIGNER_SUBJECT_INFO*, in),
                     pSignerCert (SIGNER_CERT*, in), pSignatureInfo (SIGNER_SIGNATURE_INFO*, in),
                     pProviderInfo (SIGNER_PROVIDER_INFO*, in, optional), pwszHttpTimeStamp
                     (LPCWSTR, in, optional), psRequest (PCRYPT_ATTRIBUTES, in, optional), pSipData
                     (LPVOID, in, optional), ppSignerContext (SIGNER_CONTEXT**, out)

Return value       : HRESULT (S_OK on success)
Purpose            : Signs the specified file and returns a pointer to the signed data - the original,
                     simplest member of this function family (minimum client Windows XP). Unlike
                     SignerSignEx2/SignerSignEx3, it has no dwTimestampFlags/pszTimestampAlgorithmOid
                     pair (only a single pwszHttpTimeStamp URL, implying Authenticode-style
                     timestamping only), no pCryptoPolicy, and no pDigestSignInfo. This file switched
                     from SignerSignEx3 to SignerSignEx after SignerSignEx3 reproduced the identical
                     E_INVALIDARG (see the "Investigation history" note below) - trying the smallest
                     member of the family narrows whether the failure depends on anything in the
                     newer parameters' machinery, even when they are all passed as NULL/0.

FFM notes          : `FunctionDescriptor.of(DW, DW, PTR, PTR, PTR, PTR, PTR, PTR, PTR, PTR)` - 10
                     slots: 1 return type (DW/HRESULT) followed by 9 argument layouts, one per
                     parameter listed above. Called in `_signCatalog` with: dwFlags=0 (no
                     PE-page-hash flags - irrelevant here since the subject is a .cat file, not a
                     PE); pProviderInfo=NULL (meaning "the certificate itself must already be
                     associated with a usable CSP/KSP", satisfied here since pSignerCert routes
                     through a certificate store lookup rather than a bare SPC file);
                     pwszHttpTimeStamp=NULL, psRequest=NULL (no timestamping requested - the produced
                     signature has no trusted-timestamp counter-signature, meaning it will rely
                     solely on the signing certificate's own (1-year, per Section B) validity window
                     rather than surviving past that window the way a timestamped signature would);
                     pSipData=NULL. The out-parameter ppSignerContext is always read back and, if
                     non-NULL, freed via SignerFreeSignerContext regardless of the overall HRESULT -
                     this matches Microsoft's own note (on the newer members of this family) that a
                     context may still have been allocated on certain partial-failure paths.

Windows-specific caveats relevant to this implementation:
    - Minimum supported client is Windows XP per Microsoft's own requirements table (older than both
      SignerSignEx2's Windows 8 and SignerSignEx3's Windows 10) - not a concern here since this
      backend already restricts itself to Windows 10+.
    - Microsoft's documented E_INVALIDARG case for SignerSignEx3 (dwTimestampFlags=
      SIGNER_TIMESTAMP_AUTHENTICODE combined with dwFlags=SIG_APPEND) does not apply here: this
      simpler entry point has no dwTimestampFlags parameter at all, and this file uses neither
      timestamping nor SIG_APPEND.

SECTION F - Miscellaneous Notes for Future Maintainers
====================================================================================================

FFM string-building helpers (`_wstr`, `_astr`):
    `_wstr` produces a NUL-terminated UTF-16LE buffer with 2-byte alignment - the correct native
    representation for every LPCWSTR/LPWSTR parameter in this file. `_astr` produces
    a NUL-terminated single-byte buffer with 1-byte alignment, used only for the handful of
    parameters that are genuinely ANSI/8-bit in the real Win32 prototype (OID strings passed as
    LPSTR - Crypt32's OID parameters are documented as narrow strings even in the "W" function
    variants, since OIDs are ASCII by definition and Windows does not define a wide-character OID
    type).

Arena discipline: every native call site in this file uses either the
    process-lifetime shared arena `_arena` (only for the resolved DLL/symbol lookups themselves, at
    class-init time - never for per-call data) or a `try (Arena arena = Arena.ofConfined()) { ... }`
    block scoped to a single logical operation. This means every MemorySegment built with `_wstr`/
    `_astr`/`_blob`/`_guid`/inline `arena.allocate(...)` calls is automatically reclaimed when its
    enclosing method returns - the only things that need EXPLICIT native-side cleanup are handles/
    contexts the Win32 APIs themselves allocated (kernel HANDLEs, HCERTSTORE, PCCERT_CONTEXT,
    NCRYPT_* handles, HCATADMIN, catalog HANDLEs, SIGNER_CONTEXT, and the two LocalFree-owned
    CryptEncodeObjectEx output buffers) - none of which the arena knows about or will free for you.
    This is the single most important invariant to preserve when editing this file: adding a new
    native call that returns a handle/context means adding a matching, correctly-ordered release
    call, almost always in a `finally` block, exactly like every existing call site does.

Elevation architecture (ties Section A together with the rest of the file):
    `createAndTrustProvider`/`createAndSignCatalog` (the two public entry points that need
    elevation) never touch NCrypt/Crypt32/Wintrust/Mssign32 APIs directly from the calling
    (non-elevated) process - they only build a command line and call `_runElevatedSelf`, which
    relaunches this same JVM, elevated, with a hidden marker argument (`ELEVATED_OP_ARG`) that
    routes `main()` into `_elevatedCreateAndTrustProvider`/ `_elevatedCreateAndSignCatalog` instead
    of any normal entry point. The elevated child communicates its result back to the waiting parent
    exclusively through its process exit code (read via GetExitCodeProcess) and a temp log file it
    writes before exiting - there is no shared memory or pipe across the UAC elevation boundary,
    which is a genuine Windows constraint (an elevated child runs in a different security context
    and cannot easily inherit inherited standard-handle pipes from a non-elevated parent the way
    a same-privilege child process could).
