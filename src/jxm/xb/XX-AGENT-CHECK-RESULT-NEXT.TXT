    if( gotArgCnt > reqCnt + optCnt ) throw XCom.newJXMRuntimeError(...);  // line 549
    ...

        ...
        execData.execState.setArgVar(varName, ...);  // line 556 – throws JXMException
        execData.execState.delLocalVar(varName);      // line 557 – throws JXMException
    }
    XCom.ExecuteResult xres = function.executeBody(execData);  // line 561
    execData.enShellOper = false;                               // line 564
    execData.execState.popProgState();                          // line 567

Suspected issue:
    If a JXMException is thrown by the argument-count checks (lines 548–549) or
    by setArgVar / delLocalVar (lines 556–557), the method exits via exception
    without reaching popProgState() at line 567.  The outer execute() catch
    block catches the exception, but by that point the program-state stack
    (_progStateStack, _argStack, _varStack) has an extra entry that was pushed
    but never popped.  This leaves the execution state in an incorrect
    configuration for any subsequent operation in the same run.
    execData.enShellOper is also left set to the non-default value.

Suggested change:
    Wrap the push/execute/pop section in a try-finally block so that
    popProgState() and the enShellOper reset are always executed:

        execData.execState.pushProgState(function);
        execData.enShellOper = enShellOper;
        XCom.ExecuteResult xres;
        try {
            // ... argument-count checks and argument-binding loop ...
            xres = function.executeBody(execData);
        } finally {
            execData.enShellOper = false;
            execData.execState.popProgState();
        }
        // error check, return-value save, and pending shell-ops follow here

File:  Target.java
Lines: 637-640
Content (exact):

    if( value.equals(DepForMarker) ) {
        // Save the target name
        depForTarget = depItems.get(++i);
        depForAll    = depForTarget.equals(DepForAll);

Suspected issue (1) – IndexOutOfBoundsException:
    If the DepForMarker token ("\0:\0") appears as the very last element in
    depItems, the expression depItems.get(++i) accesses a position one beyond
    the list end and throws IndexOutOfBoundsException.  This exception is a
    RuntimeException, not a JXMException, so it is not caught by the enclosing
    catch(final JXMException e) block (line 661) and propagates uncaught from
    _executeBody_getExtraDependencies().

Suggested change:
    Guard the increment with a bounds check before using ++i:

        if( value.equals(DepForMarker) ) {
            if( (i + 1) >= depItems.size() ) break; // malformed dep list
            depForTarget = depItems.get(++i);
            depForAll    = depForTarget.equals(DepForAll);
            continue;
        }

Suspected issue (2) – NPE from null list element:
    If depItems.get(++i) returns null (e.g., an evaluated variable produced a
    null entry), the immediately following depForTarget.equals(DepForAll) call
    throws NPE, which is also not caught by catch(final JXMException e).

Suggested change:
    Add a null guard after the get:

        depForTarget = depItems.get(++i);
        if(depForTarget == null) { depForAll = false; continue; }
        depForAll = depForTarget.equals(DepForAll);
