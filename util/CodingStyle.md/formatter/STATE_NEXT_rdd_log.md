| RDD_KEY_1 | `JavaModifierPriority` column order for `abstract`/`sealed`/`non-sealed`/`final`/`volatile` | STYLE_JAVA17.md §2's literal table (`abstract`/`sealed`/`non-sealed`/`final` sharing one column, ahead of `volatile`) is not purely additive against the already-COMPLETE `JavaModifierPriority`: the priority map is a single flat structure shared by `DeclarationAlignmentRule` (fields) and `GetterSetterRule` (one-liner methods), with no notion of declaration-kind context, so literally adopting the table moves `final` from column 3 to column 2 and `volatile` from column 2 to column 3 — flipping their relative render order for any group mixing `volatile` and `final` fields. Flagged to the user per the Hard Constraint's "stop and ask before changing existing behavior." User resolved with an authoritative, declaration-kind-specific breakdown: CLASS `[access] static abstract final sealed/non-sealed class`, METHOD `[access] static abstract final method`, FIELD `[access] static final volatile field`. Since `abstract`/`sealed`/`non-sealed` never co-occur with `volatile` (different declaration kinds) and `abstract`/`final`/`sealed`/`non-sealed` are mutually exclusive with each other on any single declaration, a single merged map satisfies all three orderings simultaneously: `public/private/protected=0, static=1, abstract/final/sealed=2, volatile=3`. `non-sealed` has no map entry — it lexes as three tokens (`non` `-` `sealed`), not one, so it can't be a single map key; deferred to whatever future pass needs to special-case it as a unit (no current rule reorders class/interface-level modifiers at all, so this is not yet exercised). Implemented: `JavaModifierPriority.java` map update; `TokenizerCore.java` `sealed`/`permits` added to `KEYWORDS_JAVA` (same "always-keyword, contextual-keyword-as-identifier risk accepted" precedent already set by `var`); new `JavaSpecificRule.enforcePermitsClauseLineBreaking` (STYLE_JAVA17.md §2's `permits` clause inline-vs-wrapped line-breaking, wired into `Formatter.formatOne`'s Java branch right after the Allman-brace pass). Verified via a standalone harness (Config.resolve + Formatter.formatOne, no `Main.java` yet): short `permits` clauses stay inline, long ones wrap with column-aligned permitted types, `non-sealed class` tokenizes and passes through without error, and a wrap-then-reformat round trip is byte-for-byte idempotent. |
| RDD_KEY_2 | `record` named-construct detection (brace style, closing comment, forced blank lines) | No stop-and-ask needed -- resolved by extending detection, not by changing any already-COMPLETE rendering decision. The blocker was purely mechanical: `TokenizerCore.computeConstructName()` only looks at the 2-3 tokens immediately before a `{`, which is enough for `class Foo {` but not `record Point(int x, int y) {`, where an arbitrary-length component list sits between the name and the brace. Added `"record"` to `KEYWORDS_JAVA`/`NAMED_CONSTRUCT_JAVA` (same contextual-keyword-as-identifier risk already accepted for `var`/`sealed`/`permits`), plus a small paired-stack mechanism (`bracketNameStack`/`pendingRecordName`) that captures the name when a `(` immediately follows `record IDENTIFIER`, and hands it to the *next* `{` regardless of what sits in between -- safe because Java only permits an optional `implements TypeList` there, never another brace. Generic record names (`record Box<T>(...)`) are a documented out-of-scope gap, same bounded-effort posture as `BlockStructureRule.isAnonymousClassBrace`'s qualified-name exclusion -- confirmed merely inert (no crash, no false tagging) rather than fixed. Two further additive extensions were needed because other rules independently re-derive named-construct-ness from raw tokens rather than trusting `Token.name` alone: (1) `BlockStructureRule.classifyNamed` (closing-comment label) assumed the token directly before `{` is the construct's own name, which breaks once an `implements` clause intervenes -- fixed with a new backward scanner, `findRecordComponentListClose`, that walks back over the optional `implements` clause (tracking angle-bracket depth so `implements Comparable<? super Point>`'s `super` doesn't false-positive as an unexpected keyword) to find the real component-list `)`. (2) `JavaSpecificRule.enforceMethodDefinitionAllmanBraceStyle` structurally cannot distinguish a record's own `Point(...) {` (or `... implements Shape {`) from a method definition/compact-constructor shape using only immediate-predecessor tokens -- fixed by skipping any brace the tokenizer already tagged (`Token.name != null`) before running its own method/compact-ctor heuristics, since those braces are already correctly handled elsewhere. Compact canonical constructors (`public Point { ... }`, no parameter list, STYLE_JAVA17.md §1 "ordinary method-body rules, not getter/setter one-liner rules") needed genuinely new detection in the same method, added as `isCompactConstructorBrace`. **Regression caught during verification, not by the user**: the first version of `isCompactConstructorBrace` matched *any* bare `IDENTIFIER` directly before `{` not preceded by `new`, which wrongly fired on the pre-existing, unrelated `class Foo implements Bar {` shape too (`Bar` is just as bare an IDENTIFIER as a constructor name) -- caught by diffing behavior against the pristine pre-change build on a small regression battery, not by any explicit instruction. Fixed by walking backward from the candidate name, over only access modifiers (`public`/`private`/`protected` -- the sole legal compact-constructor prefix), and requiring what remains to be a genuine member/scope boundary (`}`, `;`, `{`, or start of file); `implements`/`extends`/`,` never satisfy that, so they now correctly fail the check without needing `Token.name` (which is null for both the true- and false-positive shape here, since the tokenizer's own lookback has the identical blind spot through an arbitrary-length `implements`/`extends` clause -- a separate, pre-existing, undocumented Tier-1 gap, left untouched as out of scope for this item). Component-list line-breaking required no new code: `ScopePipeline.applySignaturePass`'s existing `)`-then-`{` signature detection already matches `record Name(...) {` and renders it via §8's signature rules, confirmed with a long component list wrapping one-component-per-line with `)` back at the `record` keyword's own column. One further documented gap, deliberately left as-is rather than fixed: a record with *both* a long component list *and* an `implements` clause does not get its component list wrapped, because `applySignaturePass` requires `)` directly before `{` just like the original `enforceMethodDefinitionAllmanBraceStyle` did -- this is the exact same "trailing qualifier between `)` and `{` blocks the wrap/restructure pass" posture already established and documented for a method's own `throws` clause, so extending past it here would be inconsistent with that precedent, not an oversight. Verified via a standalone harness (no `Main.java` yet): basic record (K&R brace, blank lines, `// record Point` closing comment, idempotent), record with `implements` (same, label still `record Point` not `implements Point`), compact constructor with an already-broken-onto-its-own-line brace and with a same-line brace needing Allman conversion, package-private compact constructor (no modifier), enum constant body with no constructor-arg parens (`ACTIVE { ... }`, the original false-positive case) confirmed still K&R/untouched, nested record inside a class, generic record name (no crash, just untagged), multiple-interface `implements` clause, long component list with and without a trailing `implements` clause, and a small regression battery (plain `class ... implements`, plain `interface ... extends`, prior `sealed`/`permits` feature, method `throws` clause, a variable literally named `record`) diffed byte-for-byte against the pristine pre-change build to confirm no behavior changed outside record's own new cases. |
| RDD_KEY_3 | concepts/`requires` implementation in `CppSpecificRule.java` | Two sub-tasks, both additive. (1) `concept` K&R brace: `BlockStructureRule.enforceKAndRBraceStyle` already places all `{` K&R by default; `enforceFunctionDefinitionAllmanBraceStyle` then moves only function-definition braces (those directly preceded by `)` after a candidate signature name) back to Allman. A `concept`'s `= requires { }` brace is preceded by `)` of the `requires(T t)` parameter list, which is preceded by `requires` -- a KEYWORD, not an IDENTIFIER -- so `isCandidateSignatureName` returns false and the Allman pass leaves it untouched. Net result: K&R is already correct for `concept` bodies with no new code. Verify via smoke test before concluding no-op. (2) `requires` and `concept` are NOT in `KEYWORDS_CPP` and `NAMED_CONSTRUCT_CPP` (confirmed from source) -- both must be added: add `"requires"` and `"concept"` to `KEYWORDS_CPP` in `TokenizerCore.java`; add `"concept"` to `NAMED_CONSTRUCT_CPP` so that `concept Drawable = ...` gets a `// concept Drawable` closing comment and blank-line insertion, same as `class`/`struct`. (3) Trailing `requires` clause placement: new `enforceRequiresClausePlacement` method in `CppSpecificRule.java`. Detection: scan for KEYWORD token with text `"requires"`. Disambiguate trailing clause from requirements expression body by looking at the previous significant token -- if it is `)`, it is a trailing clause (follows a function/template parameter list); if it is `=` or anything else, it is a requirements expression body, leave entirely untouched. For each identified trailing-clause `requires`: (a) find the preceding `)` (the parameter list close); (b) collect the full `requires ...` clause tokens up to but not including the `{` or `;` that terminates the signature; (c) if `) requires <clause>` all fits on one line within 100 chars → ensure `requires` is on the same line as `)`, done; (d) if combined exceeds 100 chars → `requires` goes on its own line indented one level under the function name's line-leading indent (reuse existing `lineIndent` helper). Nested compound requirements inside a `requires { }` body are left completely untouched -- the scan stops at `{`. Wire `enforceRequiresClausePlacement` into `Formatter.formatOne`'s `isCpp` Phase 1 block after `enforceEmptyParameterList` (line 42). All helpers needed (`prevSignificantIndex`, `nextSignificantIndex`, `lineIndent`, `matchParenBackward`) already exist in `CppSpecificRule.java`. |
| RDD_KEY_4 | `MiscRule.java` call/declaration line-breaking (options 1 and 2) -- architecture from source inspection | `parseSignature` calls `significantOnly()` at the top, which strips WHITESPACE, NEWLINE, COMMENT_LINE, and COMMENT_BLOCK tokens before any parsing. This has two consequences: (1) The checklist item "verify `parseSignature` bails on comment tokens between params" is RESOLVED as a no-op -- `parseSignature` silently ignores comments rather than bailing. This is safe for option 1 (all args dropped to one line -- comments in param lists are rare in calls/forward-decls, and the option 2 preamble-comment guard handles the important case). (2) Option 2 (preserve groups + align) MUST NOT go through `parseSignature` at all -- it needs to preserve the original line break and comment structure. Option 2 operates directly on the raw token stream, not through `Signature`/`Param`. Architecture per option: **Option 1 (dropped form):** Can reuse `parseSignature` + a new `renderDropped(Signature sig, int indentLevel, String indentStyle)` method alongside the existing `render()`. `renderDropped` joins all params on one indented line (no column alignment), preceded by a newline+indent, with `)` on its own line. Fit check: render the single params line, measure `indentLevel * INDENT_WIDTH + 1 + params.length()` -- if ≤ 100, use dropped; else fall back to existing `render()` (one-per-line). Called from a new `enforceCallLineBreaking` whole-file pass wired into `Formatter.formatOne` Phase 1 (after `enforceEmptyParameterList` for C++, after `enforcePermitsClauseLineBreaking` for Java, before `formatNonInlineSwitches` for both). Detection: scan for `(` preceded by an IDENTIFIER (same `isCandidateSignatureName` signal), NOT followed by `{` (excludes function definitions -- those are already handled by `ScopePipeline.applySignaturePass`). Collect tokens from the candidate name through the matching `)`. **Option 2 (preserve groups):** Separate method `enforceCallGroupPreservation`. Detection: same `(` scan, not followed by `{`. Check if the param list is already multi-line (contains NEWLINE between `(` and `)`). If yes: scan for leading preamble comment (COMMENT token before any arg on the first line) -- if found, leave entire arg list untouched. Otherwise: normalize spacing around `,` within each line (for calls), or apply `parseDeclaration`/`ColumnGrid` per group line (for forward declarations). Ensure `)` is on its own line. Comment-only lines between groups are left in place. Both options are wired in the same new `enforceCallLineBreaking` pass -- option 2 applied first (multi-line source, mechanically), then option 1 fallback (inline source exceeding 100 chars, dropped or one-per-line). |
