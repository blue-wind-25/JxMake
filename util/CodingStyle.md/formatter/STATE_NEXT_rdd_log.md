| RDD_KEY_1 | `JavaModifierPriority` column order for `abstract`/`sealed`/`non-sealed`/`final`/`volatile` | STYLE_JAVA17.md §2's literal table (`abstract`/`sealed`/`non-sealed`/`final` sharing one column, ahead of `volatile`) is not purely additive against the already-COMPLETE `JavaModifierPriority`: the priority map is a single flat structure shared by `DeclarationAlignmentRule` (fields) and `GetterSetterRule` (one-liner methods), with no notion of declaration-kind context, so literally adopting the table moves `final` from column 3 to column 2 and `volatile` from column 2 to column 3 — flipping their relative render order for any group mixing `volatile` and `final` fields. Flagged to the user per the Hard Constraint's "stop and ask before changing existing behavior." User resolved with an authoritative, declaration-kind-specific breakdown: CLASS `[access] static abstract final sealed/non-sealed class`, METHOD `[access] static abstract final method`, FIELD `[access] static final volatile field`. Since `abstract`/`sealed`/`non-sealed` never co-occur with `volatile` (different declaration kinds) and `abstract`/`final`/`sealed`/`non-sealed` are mutually exclusive with each other on any single declaration, a single merged map satisfies all three orderings simultaneously: `public/private/protected=0, static=1, abstract/final/sealed=2, volatile=3`. `non-sealed` has no map entry — it lexes as three tokens (`non` `-` `sealed`), not one, so it can't be a single map key; deferred to whatever future pass needs to special-case it as a unit (no current rule reorders class/interface-level modifiers at all, so this is not yet exercised). Implemented: `JavaModifierPriority.java` map update; `TokenizerCore.java` `sealed`/`permits` added to `KEYWORDS_JAVA` (same "always-keyword, contextual-keyword-as-identifier risk accepted" precedent already set by `var`); new `JavaSpecificRule.enforcePermitsClauseLineBreaking` (STYLE_JAVA17.md §2's `permits` clause inline-vs-wrapped line-breaking, wired into `Formatter.formatOne`'s Java branch right after the Allman-brace pass). Verified via a standalone harness (Config.resolve + Formatter.formatOne, no `Main.java` yet): short `permits` clauses stay inline, long ones wrap with column-aligned permitted types, `non-sealed class` tokenizes and passes through without error, and a wrap-then-reformat round trip is byte-for-byte idempotent. |
| RDD_KEY_2 | `record` named-construct detection (brace style, closing comment, forced blank lines) | No stop-and-ask needed -- resolved by extending detection, not by changing any already-COMPLETE rendering decision. The blocker was purely mechanical: `TokenizerCore.computeConstructName()` only looks at the 2-3 tokens immediately before a `{`, which is enough for `class Foo {` but not `record Point(int x, int y) {`, where an arbitrary-length component list sits between the name and the brace. Added `"record"` to `KEYWORDS_JAVA`/`NAMED_CONSTRUCT_JAVA` (same contextual-keyword-as-identifier risk already accepted for `var`/`sealed`/`permits`), plus a small paired-stack mechanism (`bracketNameStack`/`pendingRecordName`) that captures the name when a `(` immediately follows `record IDENTIFIER`, and hands it to the *next* `{` regardless of what sits in between -- safe because Java only permits an optional `implements TypeList` there, never another brace. Generic record names (`record Box<T>(...)`) are a documented out-of-scope gap, same bounded-effort posture as `BlockStructureRule.isAnonymousClassBrace`'s qualified-name exclusion -- confirmed merely inert (no crash, no false tagging) rather than fixed. Two further additive extensions were needed because other rules independently re-derive named-construct-ness from raw tokens rather than trusting `Token.name` alone: (1) `BlockStructureRule.classifyNamed` (closing-comment label) assumed the token directly before `{` is the construct's own name, which breaks once an `implements` clause intervenes -- fixed with a new backward scanner, `findRecordComponentListClose`, that walks back over the optional `implements` clause (tracking angle-bracket depth so `implements Comparable<? super Point>`'s `super` doesn't false-positive as an unexpected keyword) to find the real component-list `)`. (2) `JavaSpecificRule.enforceMethodDefinitionAllmanBraceStyle` structurally cannot distinguish a record's own `Point(...) {` (or `... implements Shape {`) from a method definition/compact-constructor shape using only immediate-predecessor tokens -- fixed by skipping any brace the tokenizer already tagged (`Token.name != null`) before running its own method/compact-ctor heuristics, since those braces are already correctly handled elsewhere. Compact canonical constructors (`public Point { ... }`, no parameter list, STYLE_JAVA17.md §1 "ordinary method-body rules, not getter/setter one-liner rules") needed genuinely new detection in the same method, added as `isCompactConstructorBrace`. **Regression caught during verification, not by the user**: the first version of `isCompactConstructorBrace` matched *any* bare `IDENTIFIER` directly before `{` not preceded by `new`, which wrongly fired on the pre-existing, unrelated `class Foo implements Bar {` shape too (`Bar` is just as bare an IDENTIFIER as a constructor name) -- caught by diffing behavior against the pristine pre-change build on a small regression battery, not by any explicit instruction. Fixed by walking backward from the candidate name, over only access modifiers (`public`/`private`/`protected` -- the sole legal compact-constructor prefix), and requiring what remains to be a genuine member/scope boundary (`}`, `;`, `{`, or start of file); `implements`/`extends`/`,` never satisfy that, so they now correctly fail the check without needing `Token.name` (which is null for both the true- and false-positive shape here, since the tokenizer's own lookback has the identical blind spot through an arbitrary-length `implements`/`extends` clause -- a separate, pre-existing, undocumented Tier-1 gap, left untouched as out of scope for this item). Component-list line-breaking required no new code: `ScopePipeline.applySignaturePass`'s existing `)`-then-`{` signature detection already matches `record Name(...) {` and renders it via §8's signature rules, confirmed with a long component list wrapping one-component-per-line with `)` back at the `record` keyword's own column. One further documented gap, deliberately left as-is rather than fixed: a record with *both* a long component list *and* an `implements` clause does not get its component list wrapped, because `applySignaturePass` requires `)` directly before `{` just like the original `enforceMethodDefinitionAllmanBraceStyle` did -- this is the exact same "trailing qualifier between `)` and `{` blocks the wrap/restructure pass" posture already established and documented for a method's own `throws` clause, so extending past it here would be inconsistent with that precedent, not an oversight. Verified via a standalone harness (no `Main.java` yet): basic record (K&R brace, blank lines, `// record Point` closing comment, idempotent), record with `implements` (same, label still `record Point` not `implements Point`), compact constructor with an already-broken-onto-its-own-line brace and with a same-line brace needing Allman conversion, package-private compact constructor (no modifier), enum constant body with no constructor-arg parens (`ACTIVE { ... }`, the original false-positive case) confirmed still K&R/untouched, nested record inside a class, generic record name (no crash, just untagged), multiple-interface `implements` clause, long component list with and without a trailing `implements` clause, and a small regression battery (plain `class ... implements`, plain `interface ... extends`, prior `sealed`/`permits` feature, method `throws` clause, a variable literally named `record`) diffed byte-for-byte against the pristine pre-change build to confirm no behavior changed outside record's own new cases. |
| RDD_KEY_3 | concepts/`requires` implementation in `CppSpecificRule.java` | Two sub-tasks, both additive. (1) `concept` K&R brace: `BlockStructureRule.enforceKAndRBraceStyle` already places all `{` K&R by default; `enforceFunctionDefinitionAllmanBraceStyle` then moves only function-definition braces (those directly preceded by `)` after a candidate signature name) back to Allman. A `concept`'s `= requires { }` brace is preceded by `)` of the `requires(T t)` parameter list, which is preceded by `requires` -- a KEYWORD, not an IDENTIFIER -- so `isCandidateSignatureName` returns false and the Allman pass leaves it untouched. Net result: K&R is already correct for `concept` bodies with no new code. Verify via smoke test before concluding no-op. (2) `requires` and `concept` are NOT in `KEYWORDS_CPP` and `NAMED_CONSTRUCT_CPP` (confirmed from source) -- both must be added: add `"requires"` and `"concept"` to `KEYWORDS_CPP` in `TokenizerCore.java`; add `"concept"` to `NAMED_CONSTRUCT_CPP` so that `concept Drawable = ...` gets a `// concept Drawable` closing comment and blank-line insertion, same as `class`/`struct`. (3) Trailing `requires` clause placement: new `enforceRequiresClausePlacement` method in `CppSpecificRule.java`. Detection: scan for KEYWORD token with text `"requires"`. Disambiguate trailing clause from requirements expression body by looking at the previous significant token -- if it is `)`, it is a trailing clause (follows a function/template parameter list); if it is `=` or anything else, it is a requirements expression body, leave entirely untouched. For each identified trailing-clause `requires`: (a) find the preceding `)` (the parameter list close); (b) collect the full `requires ...` clause tokens up to but not including the `{` or `;` that terminates the signature; (c) if `) requires <clause>` all fits on one line within 100 chars → ensure `requires` is on the same line as `)`, done; (d) if combined exceeds 100 chars → `requires` goes on its own line indented one level under the function name's line-leading indent (reuse existing `lineIndent` helper). Nested compound requirements inside a `requires { }` body are left completely untouched -- the scan stops at `{`. Wire `enforceRequiresClausePlacement` into `Formatter.formatOne`'s `isCpp` Phase 1 block after `enforceEmptyParameterList` (line 42). All helpers needed (`prevSignificantIndex`, `nextSignificantIndex`, `lineIndent`, `matchParenBackward`) already exist in `CppSpecificRule.java`. (1)'s no-op claim verified true via smoke test (idempotent, byte-identical K&R `requires(T t) { ... }` body). **Gap caught during verification, not anticipated by the plan above**: adding `"concept"` to `NAMED_CONSTRUCT_CPP` alone did not produce the closing comment, because `TokenizerCore.computeConstructName()`'s 2-token lookback (same limitation already documented for `record` in RDD_KEY_2) can't see across `concept Name = requires(params)` to reach the brace -- it saw only `)`/whatever token directly preceded `{`, found no `concept`+name pair, and tagged the brace unnamed. No stop-and-ask needed -- resolved the same way RDD_KEY_2 was, by extending detection additively, not by changing already-COMPLETE behavior. Fix, mirroring `record`'s `bracketNameStack`/`pendingRecordName` precedent but simpler (no paren-balancing needed, since nothing between `concept Name =` and the body's own `{` can open another brace): new `pendingConceptName` field, armed in `TokenizerCore.trackSignificant` when an `=` token's two immediately-preceding significant tokens are KEYWORD `concept` + an IDENTIFIER (new helper `computeConceptHeaderName`, parallel to the existing `computeRecordHeaderName`), consumed by `emitOpenBrace` (checked between `pendingRecordName` and the `computeConstructName()` fallback). Cleared without effect on a `;` reached before any `{` -- handles a body-less concept (`concept Integral = std::is_integral_v<T>;`) without misattributing the name to a later, unrelated brace; confirmed via a smoke test with exactly this shape followed by an ordinary function, which renders and Allman-converts normally with no `concept` mistagging. A second, independent gap existed in `BlockStructureRule.classifyNamed` (closing-comment label) for the same reason `record` needed `findRecordComponentListClose` in RDD_KEY_2 -- the token directly before `{` (`)` of the `requires(...)` parameter list) isn't the construct's own name, so the generic `kwIdx`/`identIdx` 2-token lookback produced a bare `Drawable` label instead of `concept Drawable`. Fixed with a new `isConceptRequiresExpressionBody` backward-scanner (predecessor chain `) requires ( ) = name concept`, via the same `matchOpenBackward` used by `findRecordComponentListClose`), checked *before* `findRecordComponentListClose` in `classifyNamed` -- required ordering, since that record check unconditionally matches on the immediate `)` predecessor with no keyword-specific gate and would otherwise misclassify this exact shape first (confirmed by trace: it resolved to a non-`record` keyword and fell through to the bare-name return, never reaching the concept check below it). Verified end-to-end via smoke tests: `concept` definition gets `// concept Drawable` and forced blank-lines-after-`{`/before-`}` (STYLE.md §7's named-construct rule, confirmed correct rather than a bug once cross-checked against that section), idempotent; re-ran the original (1)/(3) smoke tests afterward with no change in output. |
| RDD_KEY_4 | `MiscRule.java` call/declaration line-breaking (options 1 and 2) -- architecture from source inspection | `parseSignature` calls `significantOnly()` at the top, which strips WHITESPACE, NEWLINE, COMMENT_LINE, and COMMENT_BLOCK tokens before any parsing. This has two consequences: (1) The checklist item "verify `parseSignature` bails on comment tokens between params" is RESOLVED as a no-op -- `parseSignature` silently ignores comments rather than bailing. This is safe for option 1 (all args dropped to one line -- comments in param lists are rare in calls/forward-decls, and the option 2 preamble-comment guard handles the important case). (2) Option 2 (preserve groups + align) MUST NOT go through `parseSignature` at all -- it needs to preserve the original line break and comment structure. Option 2 operates directly on the raw token stream, not through `Signature`/`Param`. Architecture per option: **Option 1 (dropped form):** Can reuse `parseSignature` + a new `renderDropped(Signature sig, int indentLevel, String indentStyle)` method alongside the existing `render()`. `renderDropped` joins all params on one indented line (no column alignment), preceded by a newline+indent, with `)` on its own line. Fit check: render the single params line, measure `indentLevel * INDENT_WIDTH + 1 + params.length()` -- if ≤ 100, use dropped; else fall back to existing `render()` (one-per-line). Called from a new `enforceCallLineBreaking` whole-file pass wired into `Formatter.formatOne` Phase 1 (after `enforceEmptyParameterList` for C++, after `enforcePermitsClauseLineBreaking` for Java, before `formatNonInlineSwitches` for both). Detection: scan for `(` preceded by an IDENTIFIER (same `isCandidateSignatureName` signal), NOT followed by `{` (excludes function definitions -- those are already handled by `ScopePipeline.applySignaturePass`). Collect tokens from the candidate name through the matching `)`. **Option 2 (preserve groups):** Separate method `enforceCallGroupPreservation`. Detection: same `(` scan, not followed by `{`. Check if the param list is already multi-line (contains NEWLINE between `(` and `)`). If yes: scan for leading preamble comment (COMMENT token before any arg on the first line) -- if found, leave entire arg list untouched. Otherwise: normalize spacing around `,` within each line (for calls), or apply `parseDeclaration`/`ColumnGrid` per group line (for forward declarations). Ensure `)` is on its own line. Comment-only lines between groups are left in place. Both options are wired in the same new `enforceCallLineBreaking` pass -- option 2 applied first (multi-line source, mechanically), then option 1 fallback (inline source exceeding 100 chars, dropped or one-per-line). |
| RDD_KEY_5 | `MiscRule.enforceCallLineBreaking` -- implementation scope decisions made while building RDD_KEY_4's design (calls vs. declarations, nesting, comments, declaration-grid scope), plus one real bug found and fixed during smoke testing | Implemented as a single whole-file pass, `enforceCallLineBreaking`, scanning for `(` preceded by an IDENTIFIER with a matching `)` not followed by `{` (excludes definitions, already owned by `ScopePipeline.applySignaturePass`). Four scope decisions made without needing to stop and ask (none change already-COMPLETE behavior, all are filling in gaps RDD_KEY_4 left open): (1) **Nesting** -- once a `(` is recognized as a candidate (valid IDENTIFIER+matching-`)`), its entire interior is claimed (`scanCursor = closeIdx + 1`) and skipped for the rest of the scan, regardless of whether the candidate is ultimately rewritten or left alone (e.g. because it fits inline) -- a nested call/declaration inside another's argument list is never independently processed in the same pass; this is consistent with "no semantic grouping, no AI" (RDD_EXT_5/Step 2 NOT FEASIBLE) -- there is no mechanism to re-visit a nested candidate with different context once the outer one has decided its own layout. (2) **Comments** -- any comment token anywhere between a candidate's `(` and `)` disqualifies the *entire* candidate, left byte-for-byte untouched; this implements only the simplest case of RDD_EXT_6's comment rules (which distinguish trailing/comment-only-line/inline-block/leading-preamble) -- the fuller per-case handling is a documented, deliberate gap, not yet implemented, since no current STYLE.md worked example for *this* pass (as opposed to signature breaking) exercises the distinction and getting it wrong risks corrupting working code (same risk-calculus precedent as `CppSpecificRule`'s `(void)`/`()` two-direction split). (3) **Call vs. declaration classification** -- `parseSignature` is attempted on the candidate's `name(...)` span; success (typed params parse cleanly) means forward declaration, routed through the typed `Signature`/`Param` rendering machinery; failure means plain call, routed through raw per-argument token handling via `splitTopLevelCommas`. (4) **Declaration preserve-groups grid scope** -- per user direction (asked via AskUserQuestion since `DeclarationAlignmentRule.render()` only renders one `Declaration` per output line and could not be reused as-is for RDD_EXT_4's multi-param-per-line worked example): wrote new alignment logic specific to this case (`renderDeclarationPreserveGroups`), grouping params by original physical line and aligning by slot position across lines via `ColumnGrid` (which already supports variable-width rows, exempting each row's own last cell from padding) -- matches the spec exactly, no comment column needed since decision (2) above already disqualifies any candidate with a comment before this renderer is ever reached. **Bug found and fixed during smoke testing (real correctness issue, not a documented gap):** `renderCallDropped`/`renderCallOnePerLine`/`renderCallPreserveGroups` originally flattened argument token spans through the shared `renderTokens` helper (the same one `render()`/`renderParamsInline` use for typed param lists). `renderTokens`'s tight-attachment rules (`isTightToken`) only special-case `,`/`[`/`]`/`*`/`&`/`::`/angle-brackets -- it has never needed to know about `(`/`)` adjacency, because every *existing* caller's token lists are typed signature fragments (qualifiers, type names, array-size brackets) that never literally contain a call's parens. Once `enforceCallLineBreaking` started passing arbitrary *expression* token spans (real call arguments, which may themselves contain a nested call) through it, a nested call inside a rewritten outer candidate got its own parens spread apart by ordinary single-space joining: source `bar(1,  2)` as an argument rendered as `bar ( 1, 2 )` once the outer call needed breaking (confirmed reproducible only when the outer candidate is actually rewritten -- an outer call that fits inline never routes its arguments through any renderer, so nesting stays perfectly verbatim in that case, which is why earlier smoke tests calling out "nested call left verbatim when outer fits" passed while this one did not). Considered and rejected: extending `renderTokens`'s tight-rules to cover `(`/`)` -- correct tightness for a paren depends on whether it's a call paren (tight after an identifier) or a grouping/operator paren (`x + (a + b)`, needs a leading space), a distinction `renderTokens`'s flat token-by-token pass has no way to make reliably, and getting it wrong would be a regression in the opposite direction. Fix actually applied: new `collapseTokensToOneLine(List<Token>)` helper (whitespace/newline-run-collapsing, same precedent as the existing index-range `collapseToOneLine`, but operating on a detached sublist) used in place of `renderTokens` for all three call-argument renderers; top-level sibling arguments (found via `splitTopLevelCommas`, called directly on the raw token slice -- it already tracks paren/bracket/angle depth itself, so no `significantOnly()` pre-pass is needed) are joined with an explicit normalized `", "`, while each argument's own internal tokens (which may include a nested, unanalyzed call) are reproduced with their original spacing preserved (whitespace runs collapsed, nothing new inserted) rather than actively re-spaced -- consistent with decision (1)'s "claim and skip" posture: a nested candidate's interior was never independently analyzed, so it should ride along unprocessed rather than being normalized as if it had been. Declaration renderers (`renderDropped`/`renderOnePerLine`/`renderDeclarationPreserveGroups`) were not affected and needed no change -- their token lists are typed (`Param.typeTokens`/name/`sizeTokens`), which by construction never contain a literal `(`/`)`, so they remain correctly routed through `renderTokens`. Verified via direct smoke testing (`Formatter.formatOne`, bypassing not-yet-built `Main.java`) across 13 scenarios spanning C++ and Java, both calls and forward declarations, all four candidate forms, nesting (both outer-fits and outer-rewritten cases), comment bail-out, split-across-line leading-comma normalization, and the explicit-`(void)`-never-broken case (confirmed to be pre-existing `CppSpecificRule.enforceEmptyParameterList` behavior unrelated to this pass, not a bug -- that method already converts C++ `(void)` to `()` unconditionally per STYLE_C_CPP.md §1, well before `enforceCallLineBreaking` ever sees the candidate, so `enforceCallLineBreaking` correctly never has anything left to do there). All 13 scenarios pass after the fix; `make clean && make` succeeds with no warnings or errors. |
| RDD_KEY_6 | `Main.java` implementation (Step 1.5) -- CLI parsing, config resolution, standalone indent-style temp-cache, server auto-connect/delegate, `--server`/`--stop`, output modes, exit codes -- plus one real bug found and fixed via smoke testing, and two pre-existing gaps discovered but left unfixed as out of scope | Implementation closely follows `STATE_NEXT_EXT.md`'s Step 1.5 spec verbatim for the temp-file indent-style cache (SHA-256 hex of boundary dir path, `/tmp/style-fmt-indent-<hash>.cache`, content = style + `\n` + boundary dir `lastModified` ms, pre-populated single-entry map passed to `IndentationDetector.detect()` on a hit). Three small additive changes to other already-COMPLETE files were needed, none changing existing behavior for any pre-existing caller: (1) `IndentationDetector.findBoundaryDir` widened `private`→`public static` so `Main` can compute the same boundary dir `detect()` would have used, for the cache key/freshness check -- `detect()` itself, the method's only existing caller, is unaffected. (2) Added `ServerMode.findRunningServerPort()` (new public method, read-only, reuses the existing private `readLockfilePid`/`isProcessAlive` helpers) so `Main`'s server-auto-connect logic doesn't have to duplicate the lockfile path/format -- a divergence risk if `Main` had its own copy and the two drifted. (3) Added `ServerMode.stop()` (new public method implementing RDD_KEY_73's full stop protocol: POST `/shutdown` with short timeout, poll for lockfile removal, fall back to a new `forceKill()` helper using the same reflective-`ProcessHandle`-with-Java-8-`kill -9`-fallback pattern as the existing `isProcessAlive`) for the same reason -- `ServerMode` already owns the lockfile path constant and PID-liveness logic, so it is the natural owner of the matching stop logic too, not `Main`. **Real bug found and fixed via smoke testing:** the first version of `Main.main()` called `System.exit(run(args))` unconditionally. For `--server`, `ServerMode.start()` successfully bound the HTTP listener and returned -- but the very next line, `System.exit(...)`, immediately tore down the whole JVM (including the just-spawned listener threads) before any client could ever connect; observed directly as a background shell job reporting `Done` within the same second it printed `server listening on port ...`, instead of staying `Running`. Root cause: `ServerMode.start()` was `void`, giving the caller no way to distinguish "freshly started, must stay alive until `/shutdown` calls `System.exit` itself" from "nothing to do, already running or failed, safe to exit now" -- and `ServerMode.start()` had no caller anywhere in the codebase before this task, so changing its return type to `boolean` (true = freshly started; false = already running or startup failed) is not a behavior change to any working code path, only a new way for the one new caller to observe an outcome the method already determined internally. `Main.run()` now returns a private sentinel (`SERVER_STARTED_KEEP_ALIVE = -1`, distinct from the three real non-negative exit codes) in the freshly-started case, and `Main.main()` skips `System.exit` only then. Verified via smoke test: `--server` now stays in the background (`Running`, not `Done`), a second `--server` call against the same port correctly reports "already running" and exits 0, a client file format request auto-connects and succeeds, and `--stop` cleanly terminates it and removes the lockfile, idempotently. **`--diff` output mode** required a unified-diff implementation; no existing diff utility exists anywhere in this codebase, and shelling out to the system `diff` binary was rejected as inconsistent with the project's established no-shell-out-where-avoidable posture (already evidenced by `ServerMode.isProcessAlive`'s Linux-`/proc`-before-`kill -0`-shell-out fallback ordering). Implemented as a self-contained line-level LCS diff (`computeDiffRuns`, O(n·m) dynamic programming -- acceptable for source-file-sized inputs) producing minimal equal/delete/insert runs, then wrapped into a *single* hunk per file spanning from the first to the last changed run with context clamped to 3 lines at each end -- a deliberate simplification versus GNU `diff -u`'s behavior of splitting widely-separated change clusters into multiple hunks; still fully correct unified-diff output, just less terse for files with several far-apart edits, and far simpler to verify correct by hand than multi-hunk grouping logic. Standard "no newline at end of file" marker is not implemented (narrow edge case, no spec requirement, and source files in this project always end with a trailing newline by the time they reach this tool). **Two pre-existing gaps discovered via smoke testing, deliberately left unfixed** (not itemized in the Step 1.5 checklist, and both are existing-logic changes to already-COMPLETE files -- flagged to the user rather than silently fixed, per the Hard Constraint): (1) `ServerMode.FormatHandler.handle()` passes `config.indentStyle()` straight into `Formatter.formatOne` with no `"keep"`-resolution step (the kind `Main.formatStandalone()` now does via the temp-cache), so any project configured with `indent-style = keep` going through the *server* path throws `IllegalArgumentException` inside `MiscRule.convertIndentation` and the request fails with a 500 -- reproduced directly in smoke testing; `Main`'s server-delegation-failure-falls-back-to-standalone resilience (added independently, for general robustness against a server dying mid-request) happens to mask this in practice for CLI users, but the server-side bug itself is unfixed. (2) `Config.lineEndings()` was, before this task, read by no code anywhere (`grep` across `Formatter.java` and all rule classes confirmed zero references) -- `Main.applyLineEndings()` is the first consumer, applied only on the standalone/in-process formatting path; `ServerMode.FormatHandler` still does not apply it, so server-delegated formatting never normalizes line endings regardless of config. Both gaps are isolated to `ServerMode.java`'s existing `FormatHandler`; fixing them was judged out of scope for "implement `Main.java`" and is recorded here for a future task. Verified via manual smoke testing (no automated test harness exists yet): CLI usage errors (no args, unknown flag, exit 2), `--check` before/after formatting (exit 1 then 0), `--diff` against an unformatted file, in-place formatting, `--out DIR` (original left untouched, formatted copy written under `DIR/<filename>`), `indent-style = keep` end-to-end through the temp-cache (tabs detected and applied, cache file written with the correct two-line format), full `--server`/idempotent-restart/auto-connect-format/`--stop`/idempotent-restop lifecycle, and a 19-file `--check` sweep of the formatter's own `src/` tree (all exit 1 with zero stderr output, confirming no crashes -- the dogfood checklist items proper, including whether the resulting diffs are sane and whether `make` still succeeds after an in-place run, remain open and are intentionally not yet attempted pending user direction on scope). |
